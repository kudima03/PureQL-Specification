# PureQL Specification

PureQL is a JSON-based declarative query language for relational data. Queries are plain JSON objects validated against a JSON Schema, so they are easy to generate programmatically, serialize, transmit and validate without a parser.

The design goal is a **type system enforced by the schema itself**. Where an expression may appear, what type it has, how nulls propagate and which columns a query returns are all checked by any JSON Schema 2020-12 validator. Every expression, operators included, declares its type, so a query carries the type of each node and an interpreter reads it rather than computing it. The interpreter is left with name resolution and the few checks listed under [Validation](#validation), none of which needs type inference. Semantics are defined by this specification, not by any particular SQL dialect or host language.

`PureQL-Specification.json` is generated by `tools/generate_schema.py`; see [Tooling](#tooling).

## Quick Reference

| Property | Required | Description |
|---|---|---|
| `subqueries` | no | Named helper queries, recursive ones included, or named rows written in the query, that the main query can read from. See [Subqueries](#subqueries) |
| `from` | yes | Source to read: `{ "entity": … }` or `{ "subquery": … }`, with an optional `alias` |
| `joins` | no | Further sources, each with a join `kind` and an `on` condition. Omit rather than leave empty |
| `where` | no | Row filter, before grouping |
| `groupBy` | no | Group keys, each `{ alias, expression }` with any row expression |
| `having` | no | Group filter; only with `groupBy` |
| `select` | yes, or `aggregate` | Result columns, each `{ alias, expression }`; a column has the type its expression declares |
| `aggregate` | instead of `select` | Columns of a total query, which returns exactly one row. See [`aggregate`](#aggregate) |
| `orderBy` | no | Sort keys, each `{ expression, direction }` or `{ column, direction }`. Omit rather than leave empty |
| `distinctBy` | no | `select` aliases: of the rows equal on those columns, keep the first in `orderBy` order. Listing every alias removes duplicate rows |
| `pagination` | no | `{ skip, take }`, one of them or both, each a number from 1 or an `integer` parameter. Requires `orderBy` |
| `unionAll`, `union`, `intersect`, `except` | instead of every clause but `subqueries` | Two or more queries whose rows are combined. See [Set operations](#set-operations) |

There are four kinds of query, told apart by their shape:

- a **plain query** has `select` and returns one row per row of its sources;
- a **grouped query** has `groupBy` and `select`, and returns one row per group;
- a **total query** has `aggregate` instead of `select`, and returns exactly one row, even when there are no rows;
- a **combined query** has `unionAll`, `union`, `intersect` or `except`, and returns the rows of the queries listed there, put together.

The first three have their own rules for what their columns may read (see [Contexts](#contexts)); a combined query has no columns of its own, only those of its inputs.

## Type System

### Types

| Type | Literal value | Example |
|---|---|---|
| `integer` | JSON integer from −2⁶³ to 2⁶³ − 1: a number with no fractional part, so `5.0` counts | `42` |
| `decimal` | a JSON string holding the number in one spelling: no exponent, no leading zeros, no trailing zeros in the fraction, no `-0`; at most 28 significant digits and 28 decimal places | `"19.99"` |
| `string` | JSON string | `"active"` |
| `boolean` | `true` / `false` | `true` |
| `date` | `YYYY-MM-DD`, a real calendar date from `0001-01-01` to `9999-12-31` (February 29 only in leap years) | `"2024-01-31"` |
| `time` | `hh:mm:ss[.fraction]`: hours `00`–`23`, seconds `00`–`59`, 1 to 6 fractional digits (microseconds), the last not `0` | `"18:30:00.125"` |
| `datetime` | a `date`, `T`, a `time`, then `Z`: always in UTC (see [Temporal types](#temporal-types)) | `"2024-01-31T15:30:00Z"` |
| `uuid` | 8-4-4-4-12 hexadecimal digits in lower case, no braces or prefix | `"3f2a6c1e-8b4d-4e2a-9c1f-1a2b3c4d5e6f"` |

Every type is either non-null or nullable:

```jsonc
{ "name": "decimal" }                    // non-null
{ "name": "decimal", "nullable": true }  // nullable
```

A non-null type is written without `nullable`; `"nullable": false` is rejected, so each type has one spelling and declared types compare as written.

The schema rejects an `integer` literal outside the 64-bit range, up to the precision of JSON numbers. Its bounds are written as ±9223372036854776000, the way JavaScript prints ±2⁶³: a validator that reads numbers as binary doubles, as JavaScript does, applies exactly ±2⁶³, and one that reads them exactly lets through at most 192 more values on each side. The interpreter rejects the few values the schema lets past the real bounds. A client that reads numbers as doubles also cannot send integers beyond ±2⁵³ exactly.

### Null

There is no `null` type. A null literal always carries its type, and a literal is nullable exactly when its value is `null`:

```json
{ "type": { "name": "uuid", "nullable": true }, "value": null }
```

**Invariant:** the type of every expression is determined by its subtree and its context (row, projection, group or total, fixed by its position), never inferred from its surroundings. The context decides where fields, group keys and aggregates may appear, what `over` may hold (nothing, `"all"` or a window), and the rows an aggregate runs over, so whether `average`, `min`, `max`, `first`, `last` and the statistical aggregates can be null: always in a total query, which returns its row even over no rows. With implicit conversions this is the narrowest type: an `integer` expression is also a valid `decimal`. Every expression declares this type; see [Declared types](#declared-types).

### Implicit conversions

| From | To |
|---|---|
| `T` | `T` nullable |
| `integer` | `decimal` (and `integer?` to `decimal?`) |

The second row also lets `integer` and `decimal` values meet in `equal`, comparisons and `in`, and an `integerList` stand where a list of `decimal` is expected. There are no other conversions. `date` and `datetime` are not interchangeable, and nothing converts to `string` implicitly: every other conversion is written out with an operator (see [Conversions](#conversions)).

### Declared types

Every expression has a `type`: a field, parameter, literal or group key declares the type of the value it reads, and an operator declares the type it yields:

```json
{ "operator": "subtract", "type": { "name": "decimal", "nullable": true },
  "values": [ { "source": "orders", "field": "total",    "type": { "name": "decimal" } },
              { "source": "orders", "field": "discount", "type": { "name": "decimal", "nullable": true } } ] }
```

- **Exact.** An operator declares exactly the type it yields from the types its operands declare, as given under [Operators](#operators) and [Null semantics](#null-semantics), never a wider one. `add` of two `integer` operands is declared `integer`, not `decimal`; a lifted operator is declared nullable exactly when one of its operands is; `coalesce` is non-null exactly when one of its operands is. So an expression has one valid declared type.
- **One spelling.** Redundant spellings are rejected as well, where the form of the query alone shows them: `"nullable": false`; `and` / `or` with a single condition; an `integer` rounded to a whole number; defaults written out (`over` stating the default, a window that names nothing, a frame side of `0` rows, an `offset` of `1`, `"skip": 0`, a `mode` naming the default rule of `round`, `"direction": "asc"`, `"distinct": false`); a literal written in a second way (`decimal` `"1.50"`, `time` `"18:30:00.500"`, a `datetime` with an offset other than `Z`, a `uuid` in upper case); a repeated value in a list literal; and a `coalesce` operand that is never reached, after another non-null one (that the non-null operand comes last is beyond a schema). Equivalences between expressions are out of scope: `and(a, and(b, c))` and `and(a, b, c)`, `not(not(x))` and `x`, `not(equal(a, b))` and `notEqual(a, b)`, `if(true, a, b)` and `a` are all accepted, as any language accepts them. Nor can the schema see how a JSON number is written: `5` and `5.0` are the same `integer`.
- **Implicit conversions apply at the position, not in the declaration.** An `integer` operator stands wherever a `decimal` is expected, and a non-null one wherever a nullable one is, exactly as a field would.
- **Checked by the schema.** A position reads only the type its operand declares, and each operator checks its declared type against its operands' declared types. Each node is therefore validated once, and validation time grows linearly with the size of the query, whatever its depth.
- **Read by the interpreter.** The type of any node is the one it declares, so building a typed expression tree needs no type computation.
- **Columns and keys.** A `select` column and a `groupBy` key have the type their expression declares; they carry no `type` of their own. So the result schema of a query is read from `select[i].expression.type`, and a key reference `{ "key": <alias>, "type": … }` repeats the type of that key's expression.

### Null semantics

PureQL uses the following null semantics:

- **Lifted operators:** arithmetic (`integerDivide` and `modulo` included), powers and logarithms, trigonometry, `concat`, `length`, `upper` / `lower`, `foldCase`, `normalize`, `removeDiacritics`, `trim` / `trimStart` / `trimEnd`, `substring`, `replace`, `position`, `splitPart`, `padStart` / `padEnd`, `repeat`, `reverse`, `replaceRegex`, date/time math, parts and `startOf…`, `dateFromParts` / `timeFromParts` / `datetimeFromParts`, the conversions, `abs`, `sign`, `round`, `truncate`, `floor`, `ceiling`, `greatest` and `least`. A nullable operand makes the result nullable, and the result is `null` when any operand is `null`. Operands named by their role count as well: the `exponent` of `power`, the `base` of `log`, the `digits` of `round` and `truncate`, `start` and `length`, `pattern` and `replacement`, `delimiter` and `index`, `fill` and `count`. An operand that may be absent (`digits`, `length`, the `start` of `position`) counts only when it is written ([`071_lifted_over_every_operand.json`](samples/valid/071_lifted_over_every_operand.json)). What stays non-null is what is not such an operand: the items of `removables`, the `separator` of `concatWith` (which is not lifted), the `default` of `previous` / `next`, everything that is a literal or a parameter (a regular expression and its `group`, the `separator` of `concatAll`, `fraction`, `offset`, `buckets`, `maxDepth`), and the names `form` of `normalize` and `mode` of `round`, which are never expressions and never `null`.
- **`zone`:** an operator that reads a `datetime` in a [time zone](#time-zones) is lifted over its `zone` as over any operand: a `null` zone gives `null`.
- **`if`:** the result is nullable when either branch is nullable, and its value is the value of the branch taken, so `if(true, 1, null)` is `1`.
- **Comparisons:** `equal`, `notEqual`, ordering comparisons and `in` accept nullable operands and return a non-null `boolean`. `null == null` is `true`. An ordering comparison with one `null` operand is `false`; with two, it holds exactly when it holds for two equal values, so `greaterThanOrEqual` and `lessThanOrEqual` are `true` and `greaterThan` and `lessThan` are `false`. `greaterThanOrEqual(a, b)` is therefore `or(greaterThan(a, b), equal(a, b))` for every operand; see [Ordering and equality](#ordering-and-equality). A `null` value is `in` a list exactly when the list contains `null`, which only a nullable subquery column can. This holds in every clause, `join.on` included.
- **String matching:** `contains`, `startsWith` and `endsWith` accept nullable operands and return a non-null `boolean` too, so they are conditions as they are. The result is `false` when either operand is `null`, also when both are: unlike `equal`, a `null` string neither contains nor is contained in anything.
- **Reading text:** `asInteger` … `asUuid` of a string are lifted like the other conversions. `tryAs…` accepts a nullable string and is always nullable: `null` when the string is `null` or is not written as a literal of the type.
- **Regular expressions:** `matchesRegex` accepts a nullable operand and returns a non-null `boolean`, `false` for `null`, like `contains`. `extractRegex` accepts one too and is always nullable: `null` when the operand is `null` or when nothing matches. `replaceRegex` is lifted.
- **`concatWith`:** accepts nullable operands and returns a non-null `string`: `null` operands are skipped, where `concat` is lifted and gives `null`.
- **Conditions:** `where`, `having`, `join.on`, `and` / `or` / `not`, `if.condition` and aggregate `predicate` require a non-null `boolean`. To use a nullable boolean as a condition, write `equal(x, true)` or `coalesce(x, false)`.
- **`coalesce`:** non-null as soon as one operand is non-null.
- **`nullIfEqual`:** accepts nullable operands and is always nullable, even over two non-null ones: `null` when its operands are equal, as `equal` compares them, and its left operand otherwise.
- **`previous` / `next`:** `null` where the partition has no row at that position, unless a `default` is given; a `null` read from the other row is returned as it is. The ranking functions are never null.
- **Sorting:** `null` sorts before every value in ascending order and after every value in descending order.

### Numbers

| Operation | Result |
|---|---|
| `add`, `subtract`, `multiply`, `greatest`, `least` | `integer` when every operand is `integer`, otherwise `decimal` |
| `divide` | always `decimal`. There is no truncating division by accident |
| `power`, `sqrt`, `exp`, `ln`, `log10`, `log` | always `decimal`, also over `integer` operands |
| `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `pi` | always `decimal`; angles are in radians |
| `integerDivide` | `integer`, whatever its operands |
| `modulo` | `integer` for `integer` operands, `decimal` when an operand is a `decimal` |
| `floor`, `ceiling`, `round`, `truncate` | `integer`. `round` and `truncate` with `digits` keep the type of their operand: `decimal` of a `decimal`, `integer` of an `integer`. Without `digits` the operand declares `decimal`: an `integer` is already whole |
| `abs` | the type of its operand: `integer` stays `integer` |
| `sign` | `integer`: `-1`, `0` or `1` |

Range, precision, rounding, `integerDivide` / `modulo` signs and division by zero are defined under [Integer and decimal arithmetic](#integer-and-decimal-arithmetic).

### Temporal types

- **`date`** is a local calendar date, and **`time`** a local time of day. Neither has an offset.
- **`datetime`** is an instant, a point on the global timeline:
  - It is always written in UTC, ending in `Z`, with `T` and `Z` in upper case. An instant has one spelling: `2024-01-01T03:00:00+03:00` is written `2024-01-01T00:00:00Z`, and any other offset, `+00:00` included, is rejected.
  - Comparison, `equal`, `*DiffSeconds`, `min` / `max`, `orderBy`, `groupBy` and `distinctBy` all work on the instant, and `datetime` results are returned in UTC, written with `Z`.
  - It has no time zone of its own. An operator that reads a calendar date or a time of day from it reads it in UTC, or in the time zone it is given as `zone`: see [Time zones](#time-zones).
  - A `datetime` parameter is bound in UTC too. If storage holds naive timestamps, how they map to instants is interpreter configuration and is never guessed.

Literal patterns use `[0-9]`, never `\d`, no lookahead, and reject newlines explicitly. Python's `re` treats `\d` as any Unicode digit and lets `$` match before a final newline, while ECMA-262 does neither, and lookahead support varies, so these rules keep every validator in agreement.

## Building Blocks

| Node | Shape | Notes |
|---|---|---|
| Field | `{ "source": "orders", "field": "total", "type": { "name": "decimal" } }` | `source` is an entity, a subquery or an alias of either |
| Literal | `{ "type": { "name": "string" }, "value": "active" }` | Always non-null unless `value` is `null` |
| Parameter | `{ "param": "since", "type": { "name": "datetime" } }` | Bound at execution time; may be nullable |
| List | `{ "type": { "name": "stringList" }, "value": ["a", "b"] }`, a list parameter `{ "param": …, "type": { "name": "stringList" } }`, or a subquery column | A value, not a column. Accepted only by `in`. A list literal holds at least one value and no `null`, and a list type is never nullable. `in` over no values would be the literal `false`; a set that may be empty is a list parameter or a subquery column. Every type `T` has `TList` |
| Group key | `{ "key": "user_id", "type": { "name": "uuid" } }` | The `alias` of a `groupBy` key, repeating the type the key's expression declares; only in grouped `select`, `having` and `orderBy` |
| Operator | `{ "operator": "add", "type": { "name": "integer" }, "values": [ … ] }` | Declares the type it yields, exactly. See [Declared types](#declared-types) and [Operators](#operators) |

Fields, parameters and group keys declare their type at the point of use, including nullability, and the declaration must match exactly. For example, a field read from the optional side of an outer join is declared nullable, and a non-null field elsewhere is declared non-null. Operators declare their result type the same way, and the schema checks it against their operands.

Names of entities, fields, aliases, parameters and subqueries are non-empty, have no leading or trailing space or tab, and contain no line break. Inner spaces and any other characters are allowed, e.g. `"order items"`.

## Contexts

There is one set of operators. Where an expression may appear is decided by its **context**, which is fixed by its position in the query:

| Context | Used in | Fields | Group keys | Aggregates |
|---|---|---|---|---|
| row | `where`, `join.on`, `groupBy` keys, aggregate `selector` / `predicate` / `orderBy`, a window's `partitionBy` / `orderBy`, the `operand` / `default` of `previous` / `next`, the `select` of a recursive `next` without `groupBy` | yes | no | no |
| projection | `select` / `orderBy` of a plain query | yes | no | over all rows, or over a [window](#windows) with `over` |
| total | `aggregate` of a total query | no | no | over all rows, without `over` |
| group | `select` / `having` / `orderBy` of a grouped query, `select` / `having` of a recursive `next` with `groupBy` | no | yes | over the group, or over all rows with `over: "all"` |

Consequences, all enforced by the schema:

- Aggregates cannot appear in `where` or `join.on`, and cannot nest: an aggregate body is in row context.
- A grouped query cannot select, filter on or sort by a bare field. Use a group key or an aggregate.
- Group keys exist only in grouped queries.
- Window functions (an aggregate with a window, the ranking functions, `previous` / `next`) exist only in the `select` and `orderBy` of a plain query, and not in the `next` of a recursive subquery, which has no projection context.
- Window functions do not nest: the parts of a window and the operands of `previous` / `next` are in row context.
- A total query reads fields only inside aggregates, and has no `orderBy`, `distinctBy`, `pagination` or `having`.

## Query Clauses

A query runs in this order: `from` and `joins`, `where`, `groupBy`, `having`, `select` (or `aggregate`), `orderBy`, `distinctBy`, `pagination`. Aggregates over all rows see the rows left by `where`, and so do [window functions](#windows), which are computed with `select`. Each step is defined under [Evaluation](#evaluation).

### `from` and `joins`

```json
"from":  { "entity": "orders", "alias": "o" },
"joins": [
  { "kind": "left", "entity": "coupons",
    "on": { "operator": "equal", "type": { "name": "boolean" },
            "left":  { "source": "o",       "field": "coupon_id", "type": { "name": "uuid", "nullable": true } },
            "right": { "source": "coupons", "field": "id",        "type": { "name": "uuid" } } } }
]
```

- A source names exactly one of `entity` or `subquery`, plus an optional `alias`. Aliases allow joining the same source twice (self-join).
- Join kinds (`kind`): `inner`, `left`, `right`, `full`.
- `on` is a non-null boolean in row context.
- **Nulls in `on`.** `on` has the same null semantics as every other clause, so `equal` on two nullable keys pairs the rows whose keys are both `null`. This differs from SQL `=`. To match only non-null keys, add `notEqual(key, null)`, as in [`075_join_on_nullable_key.json`](samples/valid/075_join_on_nullable_key.json). A join where either key is non-null, such as a foreign key to a primary key, is unaffected.
- **Translating to SQL.** `equal` with at least one non-null operand is plain `=`. With two nullable operands it is `IS NOT DISTINCT FROM`, which some databases cannot use for hash joins or indexes, so a `notEqual(key, null)` guard also lets the interpreter emit `=`.
- **Nullability after an outer join.** A field is nullable at a point of the query if it is stored nullable, or if its source is on the optional side of an outer join that precedes that point: the joined source for `left`, every earlier source for `right`, both for `full`.
  - A join's own `on` precedes the join itself, so it sees the joined source's real rows. In the example, `coupons.id` is non-null in its own `on` and nullable everywhere after it.
  - The `on` of a later join, `where`, `groupBy`, `select` and every later clause come after the join. A field that is non-null in storage is therefore nullable in the next join's `on` if its source was joined with `left` before, as in [`079_outer_join_chain.json`](samples/valid/079_outer_join_chain.json), and every earlier source is nullable after a `right` join, though not in that join's own `on`, as in [`080_right_join_after_left_joins.json`](samples/valid/080_right_join_after_left_joins.json).
  - An `on` is never affected by joins that come after it: a `right` join makes the earlier sources nullable only from that join on.
  - References declare exactly this nullability, no more and no less: declaring a non-null field nullable is an error too.

### `where`

A non-null boolean in row context, evaluated per row after the joins. A boolean field is a condition on its own.

### `groupBy` and group keys

`groupBy` lists one or more keys:

```json
{ "alias": "days_to_ship",
  "expression": { "operator": "dateDiffDays", "type": { "name": "integer", "nullable": true },
                  "left":  { "source": "orders", "field": "shipped_date", "type": { "name": "date", "nullable": true } },
                  "right": { "source": "orders", "field": "order_date",   "type": { "name": "date" } } } }
```

- **Expression.** A key may be any row expression, including a computed one such as a `dateDiffDays` or an `if` bucket.
- **Type.** A key has the type its expression declares. Here `shipped_date` is null until an order ships, so the lifted `dateDiffDays` and the key are `integer?`, and unshipped orders form one group with a `null` key.
- **Alias.** Every key has an `alias`, unique among the keys of the query.
- **Referencing.** A key is referenced by its alias as `{ "key": "days_to_ship", "type": … }`, and the reference repeats the type of the key's expression exactly. Matching the two is therefore a plain lookup, and reordering the keys changes nothing.
- **Use.** A key behaves like an ordinary value of its type: it can be selected, compared, used in arithmetic and sorted.
- **Result.** Keys are **not** added to the result automatically; select the ones you need.

### `having`

A non-null boolean in group context. It requires `groupBy`.

### `select`

Every column has an alias and an expression:

```json
{ "alias": "revenue",
  "expression": { "operator": "sum", "type": { "name": "decimal" },
                  "selector": { "source": "orders", "field": "total", "type": { "name": "decimal" } } } }
```

A column has the type its expression declares, here `decimal`, which the schema has checked like every other declaration. So every query has a declared and verified result schema: an alias and a type per column. A column is never wider than its expression: a sum of `integer` values is an `integer` column.

- **Plain query:** one row per row left by `where`, whatever the columns read. Aggregates, which run over all rows unless they have a [window](#windows), are repeated on every row, and a `select` of only literals returns one row per row too. For a single row, use [`aggregate`](#aggregate).
- **Grouped query:** one row per group.

### `aggregate`

A total query has `aggregate` instead of `select`, with the same `{ alias, expression }` columns:

```json
{ "from": { "entity": "orders" },
  "aggregate": [
    { "alias": "orders",  "expression": { "operator": "count", "type": { "name": "integer" } } },
    { "alias": "largest", "expression": { "operator": "max", "type": { "name": "decimal", "nullable": true },
                                          "selector": { "source": "orders", "field": "total", "type": { "name": "decimal" } } } } ] }
```

It returns exactly one row, even when `where` leaves no rows. Its columns are in total context: they read fields only inside aggregates, and every aggregate runs over all rows, so `over` is not written. With no rows, `count`, `countDistinct` and `sum` are `0`, `concatAll` is the empty string, and `min`, `max`, `average`, `first`, `last` and the statistical aggregates are `null`, so these are always nullable here. A total query has no `orderBy`, `distinctBy` or `pagination`, which would act on its one row, and no `having`: filter with `where`. As a subquery it gives a one-row source, e.g. joined `on` the literal `true` next to every row.

### `orderBy`

Each item is `{ "expression": … }` for ascending order or `{ "expression": …, "direction": "desc" }` for descending; `"asc"` is never written. The expression is in projection context for a plain query and group context for a grouped one, and may be of any type. Each type orders as defined under [Ordering and equality](#ordering-and-equality). Items apply in order, each breaking the ties of the previous one.

A sort key can also name a column of the query's own `select` by its alias, as `distinctBy` does: `{ "column": "revenue", "direction": "desc" }`. The key is then the value of that column, so a computed column that is also sorted by, an aggregate, a window function or a long expression, is written once and cannot drift from its copy ([`045_order_by_column.json`](samples/valid/045_order_by_column.json)).

- An item has `expression` or `column`, never both. A column is not an expression: it declares no type and takes none, and it cannot appear inside one. To sort by something computed from a column, write the expression.
- `column` exists in the `orderBy` of a query only. The `orderBy` of a window, of `first`, `last` and `concatAll` sort rows before `select` has run, and take row expressions.
- A plain field that is also a column may be written either way.

### `distinctBy` and `pagination`

`distinctBy` lists `select` aliases, each once. Of the rows equal on those columns, compared with `equal`, it keeps the first in `orderBy` order and drops the others:

```json
"orderBy": [ { "expression": { "source": "orders", "field": "ordered_at", "type": { "name": "datetime" } }, "direction": "desc" },
             { "expression": { "source": "orders", "field": "id", "type": { "name": "uuid" } } } ],
"distinctBy": [ "user_id" ]
```

keeps each user's latest order ([`015_distinct_by_first_row.json`](samples/valid/015_distinct_by_first_row.json)). Listing every alias removes duplicate rows, as SQL `DISTINCT` does; rows equal in every column are interchangeable, so no order is needed then. Otherwise, which row is kept is defined only as far as `orderBy` tells the rows apart, as with pagination below. Without `distinctBy` duplicate rows are kept.

`pagination` is `{ "skip": ≥ 1, "take": ≥ 1 }` with one of the two or both: `skip` rows are passed over, then at most `take` are returned. Each is its own default when absent, so a first page is `{ "take": 20 }`, never `"skip": 0`, and `{ "skip": 10 }` returns every row after the first ten ([`017_rows_after_the_first.json`](samples/valid/017_rows_after_the_first.json)). It requires `orderBy`, since without an order two interpreters may return different pages. The order should also be total: rows equal on every `orderBy` key may fall on either side of a page boundary, so end the keys with one that identifies a row, such as an `id`. The schema cannot check this, as it does not know which columns are unique. Each of `skip` and `take` is either a number or a non-null `integer` parameter, e.g. `{ "skip": { "param": "offset", "type": { "name": "integer" } }, "take": 20 }`, so the page is chosen at execution time. The schema checks the range of a number; a `skip` parameter may be bound to `0`, which skips nothing, and binding a parameter outside its range (a negative `skip`, a `take` below 1) is an execution error. Aggregates over all rows and window functions are computed before `distinctBy` and `pagination`.

### Subqueries

The main query may declare named helper queries:

```json
{
  "subqueries": [
    { "name": "user_totals", "query": { "from": { "entity": "orders" }, "groupBy": [ … ], "select": [ … ] } },
    { "name": "big_spenders", "query": { "from": { "subquery": "user_totals" }, "where": …, "select": [ … ] } }
  ],
  "from": { "entity": "users" },
  "joins": [ { "kind": "inner", "subquery": "big_spenders", "on": … } ],
  "select": [ … ]
}
```

- A subquery is read through `from` / `join` `{ "subquery": <name> }`. Its columns are fields: `{ "source": <name or alias>, "field": <column alias>, "type": … }`.
- `in` accepts one column of a subquery as its list, which gives a semi-join or, with `not`, an anti-join: `{ "subquery": <name>, "field": <column alias>, "type": … }`.
- The list is flat: subqueries cannot declare subqueries. A subquery reads the subqueries declared before it, and only a recursive one, described below, reads itself.

A subquery entry can hold `rows` instead of a `query`: rows written in the document itself, for a short reference list that no entity holds, such as statuses with their order or the months of a year ([`110_inline_rows.json`](samples/valid/110_inline_rows.json)).

```json
{ "name": "statuses",
  "rows": [
    [ { "alias": "status", "expression": { "type": { "name": "string" },  "value": "new" } },
      { "alias": "rank",   "expression": { "type": { "name": "integer" }, "value": 1 } } ],
    [ { "alias": "status", "expression": { "type": { "name": "string" },  "value": "paid" } },
      { "alias": "rank",   "expression": { "type": { "name": "integer" }, "value": 2 } } ] ] }
```

- **Cells.** Each row is a list of `{ alias, expression }`, like a `select`, where an expression is a literal or a parameter. A cell carries its type, as every literal does, and nothing is computed: a column computed from them belongs to the query that reads the rows.
- **Columns.** Every row has the same aliases, in any order, and the columns come in the order of the first row. A column takes the least type that accepts its cell in every row, as a column of a [set operation](#set-operations) does: an `integer` and a `decimal` cell give `decimal`, and a `null` cell or a nullable parameter makes the column nullable.
- **Use.** Inline rows are a subquery like any other: unordered, read with `from`, `join` or `in`, and declared before the subqueries that read them. One row of parameters joined `on` the literal `true` puts those values next to every row.
- **At least one row,** each with at least one column. A set that may be empty, or that a client sends, is an `in` list parameter.

A subquery entry can also be **recursive**: it reads its own rows, to follow a hierarchy of any depth, such as everyone a user referred, directly or through others ([`120_descendants.json`](samples/valid/120_descendants.json)).

```json
{ "name": "referrals",
  "recursive": {
    "seed": { "from": { "entity": "users" }, "where": <users.id = :user_id>,
              "select": [ { "alias": "id",    "expression": <users.id> },
                          { "alias": "depth", "expression": { "type": { "name": "integer" }, "value": 0 } } ] },
    "next": { "from": { "entity": "users" },
              "joins": [ { "kind": "inner", "subquery": "referrals", "on": <users.referrer_id = referrals.id> } ],
              "select": [ { "alias": "id",    "expression": <users.id> },
                          { "alias": "depth", "expression": <add(referrals.depth, 1)> } ] },
    "maxDepth": 50 } }
```

- **`seed`** is a query of any kind and gives the first rows. It does not read the subquery itself.
- **`next`** gives the rows that follow from the rows before. It reads the subquery under its own name, which stands there for the rows of the previous level only, and it is run again on the rows it has just produced, until it produces none. It has `from`, `joins`, `where` and `select`, and no `orderBy`, `distinctBy` or `pagination`. Without `groupBy` it gives one row for each row it reads: its columns are row expressions, so it has no aggregates and no window functions. With `groupBy` it is a grouped query: see *Steps that aggregate* below.
- **One reference.** `next` reads the subquery exactly once, in `from` or as a joined source, and not on the optional side of an outer join. Like any subquery it may also read entities and the subqueries declared before it.
- **Columns.** The columns of the subquery are those of `seed`, with its aliases and types. `next` has the same aliases, each of a type the seed's column accepts: the same type, an `integer` for a `decimal` column, a non-null value for a nullable one. So a column that `next` may fill with `null`, or with a `decimal`, is declared that way in `seed`: with a typed `null` literal, or with `asNullable` or `asDecimal` around the seed's value. Every reference to a column of the subquery, also inside `next`, declares the seed's type.
- **Every row is returned.** The result holds the rows of `seed` and of every run of `next`, duplicates included, as `unionAll` would give them: a row reached along two paths is there twice. It is unordered, like every subquery.
- **`maxDepth`** is required: a number from 1, or a non-null `integer` parameter. The rows of `seed` are at depth 0 and each run of `next` is one level deeper. A row beyond `maxDepth` is an [execution error](#execution-errors), so data with a cycle fails the query; it neither runs forever nor returns a result that was cut off. To stop at a level on purpose, filter in `next`, e.g. with a `where` on a depth column. To walk data that may hold cycles, carry the path and skip a row that is already on it.
- **Depth and path** are ordinary columns: `0` in `seed` and `add(depth, 1)` in `next`, and a path that `next` extends with `concat`. Sorting by the path lists a tree in reading order ([`122_tree_in_order.json`](samples/valid/122_tree_in_order.json)).
- **Steps that aggregate.** With `groupBy`, and `having` if needed, `next` gives one row for each group of the rows it reads. Its columns and its `having` are then in group context, as in any [grouped query](#groupby-and-group-keys): they read group keys and aggregates, and `over: "all"` is every row of the step. So a step can merge the rows of a level, e.g. a user reached along several paths becomes one row, and it can compute from a sum over data, which is how a numerical method iterates.
  - **An iteration** keeps its state in the columns of the subquery, one row for each thing it computes. `next` joins that row with the data, groups by the columns of the state, and returns the next state from aggregates over the data. [`125_rate_of_return_by_iteration.json`](samples/valid/125_rate_of_return_by_iteration.json) finds the internal rate of return of each investment by Newton's method: the state is a rate, and each step moves it by the net present value of the cash flows divided by its slope.
  - **It stops when a level is empty**, as every recursive subquery does: when `where` keeps no row of the level before, or `having` drops every group. So the stop rule is a condition of the query, such as a tolerance in `having` (`abs(sum(…))` above `0.0000001`) or a number of steps in `where`. There is no `until` and no tolerance setting.
  - **`maxDepth` still bounds it.** An iteration that has not stopped by then is an [execution error](#execution-errors), never a result that did not converge.
  - **The result holds every level**, so the final state is the row of the last step. Carry a `step` column and read the latest row of each key, with `orderBy` and `distinctBy`.
  - **Not a total query.** `next` has no `aggregate` form: a total query returns a row even over no rows, so its levels would never be empty. A step over every row groups by the columns of the state, which all rows of the level before share.
  - **The same digits everywhere.** `decimal` arithmetic is exact and rounds by fixed rules, so an iteration takes the same path in every interpreter. For the cash flows −1000, 300, 420 and 680 in periods 0 to 3, four steps take the rate from `0.1` to `0.163406`, where the net present value is within the tolerance. Dated cash flows work the same way, with `divide(dateDiffDays(date, first), 365)` as the exponent.
  - **In SQL.** Most engines do not allow an aggregate in the recursive part of a recursive query, so an interpreter that compiles to SQL runs such a subquery level by level, one statement for each. It is the one construct of the language that may not compile to a single statement; a `next` without `groupBy` does.
- **Use.** A recursive subquery is read like any other, by the main query and by later subqueries. `next` can walk up instead of down, to the chain of referrers above a user ([`121_ancestors.json`](samples/valid/121_ancestors.json)). Seeded with every row as its own ancestor, it pairs each row with everything below it, which a grouped query rolls up ([`123_tree_roll_up.json`](samples/valid/123_tree_roll_up.json)). It also makes rows that no entity holds, such as a day for each date in a range ([`124_calendar_of_days.json`](samples/valid/124_calendar_of_days.json)).

### Set operations

A combined query puts the rows of two or more queries together. It has one of four properties, each holding the queries to combine, and no other clause:

```json
{ "unionAll": [
    { "from": { "entity": "orders" },
      "select": [ { "alias": "at",   "expression": { "source": "orders", "field": "ordered_at", "type": { "name": "datetime" } } },
                  { "alias": "kind", "expression": { "type": { "name": "string" }, "value": "placed" } } ] },
    { "from": { "entity": "orders" },
      "select": [ { "alias": "at",   "expression": { "source": "orders", "field": "shipped_at", "type": { "name": "datetime" } } },
                  { "alias": "kind", "expression": { "type": { "name": "string" }, "value": "shipped" } } ] } ] }
```

| Operation | Result |
|---|---|
| `unionAll` | every row of every input, duplicates kept |
| `union` | the same rows, each distinct row once |
| `intersect` | the distinct rows that every input returns |
| `except` | the distinct rows of the first input that no other input returns |

- **Inputs.** At least two queries of any kind: plain, grouped, total, or combined again, so `(a union b) except c` is an `except` whose first input is a `union`. An input reads entities and subqueries like any query, and does not declare subqueries.
- **Columns** are matched by alias, not by position: every input has the same aliases, in any order, and the result lists them in the order of the first input. A column takes the least type that accepts it in every input: `integer` and `decimal` give `decimal`, and it is nullable if it is nullable in any input. Types that do not meet this way, such as `date` and `datetime`, are an error.
- **No clause of its own.** A combined query is unordered and has no `where`, `orderBy`, `distinctBy` or `pagination`. To filter, sort, deduplicate by columns or page the combined rows, declare it as a subquery and read it with `from`, as [`108_union_all.json`](samples/valid/108_union_all.json) does. Its inputs are unordered too: as in a subquery, an input has `orderBy` only together with `pagination` or `distinctBy`, e.g. the ten latest orders of each kind.
- **Where it stands.** Wherever a query does: as the main query, which may declare `subqueries` next to the operation ([`109_union_intersect_except.json`](samples/valid/109_union_intersect_except.json)), or as the `query` of a subquery.

## Operators

The tables use `T` for any type and `T?` for its nullable form. Every operator node also has a `type`: the result in the last column, declared exactly (see [Declared types](#declared-types)). Unless stated otherwise, the result is nullable exactly when an operand is: arithmetic, powers and logarithms, trigonometry, `concat`, `length`, `upper` / `lower`, `foldCase`, `normalize`, `removeDiacritics`, `trim` / `trimStart` / `trimEnd`, `substring`, `replace`, `position`, `splitPart`, `padStart` / `padEnd`, `repeat`, `reverse`, `replaceRegex`, date and time math, parts and `startOf…`, `dateFromParts` / `timeFromParts` / `datetimeFromParts`, the conversions, `abs`, `sign`, `round`, `truncate`, `floor`, `ceiling`, `greatest` and `least` are lifted (see [Null semantics](#null-semantics)), over every operand a row lists, those named by their role included.

### Boolean and comparison

| Operator | Shape | Result |
|---|---|---|
| `and`, `or` | `{ conditions: [boolean, …] }` (at least 2) | `boolean` |

### Conversions

| Operator | Shape | Result |
|---|---|---|
| `asString` | `{ operand: T }`, `T` any type but `string` | `string`: the value as a literal of `T` is written |
| `asDate` | `{ operand: datetime, zone?: string }` / `{ operand: string }` | `date`: the day of a `datetime`, in UTC or in `zone`, or the date a string spells |
| `asTime` | `{ operand: datetime, zone?: string }` / `{ operand: string }` | `time`: the time of day of a `datetime`, in UTC or in `zone`, or the time a string spells |
| `asDatetime` | `{ operand: date, zone?: string }` / `{ operand: string }` | `datetime`: midnight of a `date`, in UTC or in `zone`, or the instant a string spells |
| `asInteger`, `asBoolean`, `asUuid` | `{ operand: string }` | the type in the name: the value a string spells |
| `asDecimal` | `{ operand: integer }` / `{ operand: string }` | `decimal`: an `integer` as a `decimal`, or the number a string spells |
| `asNullable` | `{ operand: T }`, `T` any type, non-null | `T?`: the same value, declared nullable |
| `tryAsInteger`, `tryAsDecimal`, `tryAsBoolean`, `tryAsDate`, `tryAsTime`, `tryAsDatetime`, `tryAsUuid` | `{ operand: string? }` | the type in the name, always nullable: `null` for text that is not a literal of it |

Each `as…` operator yields the type in its name and takes only the types it changes: there is no `asString` of a `string` and no `asDate` of a `date`.

- **`asString` and the conversions between temporal types never fail.**
- **Reading a string depends on the data.** `as…` of a string is an [execution error](#execution-errors) when the text is not a literal of the type, for values that must be right. `tryAs…` gives `null` instead, so that dirty source data does not break a whole report, and `coalesce` over it supplies a default. The `tryAs…` operators read only strings, since nothing else can fail.
- **The other conversions need no operator.** A `decimal` becomes an `integer` with `round`, `floor`, `ceiling` or `truncate`, which say how; a `boolean` becomes a number with `if`, and a number a `boolean` with a comparison. So `asInteger`, `asBoolean` and `asUuid` take a string only.
- **Widening is implicit at a position and explicit where there is none.** An `integer` stands wherever a `decimal` is expected, and a non-null value wherever a nullable one is. A `select` column, a `groupBy` key, the `operand` of `previous` / `next`, the `left` of `nullIfEqual` and a column of a recursive `seed` are not such positions: there the expression itself fixes the type. `asDecimal` of an `integer` and `asNullable` state the wider type there ([`062_explicit_widening.json`](samples/valid/062_explicit_widening.json)):
  - `asDecimal` of an `integer` is that number as a `decimal`. It is lifted and never fails; `asDecimal` of a `decimal` is rejected, and `tryAsDecimal` still reads strings only.
  - `asNullable` takes a non-null operand of any type and yields the same value declared nullable. The name of the type is kept: an `integer` gives `integer?`, never `decimal?`. The value is never `null`; a nullable operand is rejected, being the one type the operator would not change. Nothing does the reverse: a nullable value becomes non-null with `coalesce`.

The text each type gives, and reads, is defined under [Conversion results](#conversion-results).

### Conditional and null handling

| Operator | Shape | Result |
|---|---|---|
| `if` | `{ condition: boolean, then: T, else: T }` | `T` (`T?` if either branch is nullable; `decimal` if either branch is) |
| `coalesce` | `{ values: [T?, …] }` (at least 2) | `T` if any operand is non-null, otherwise `T?`; `decimal` if any operand is |
| `greatest`, `least` | `{ values: [T, …] }` (at least 2), `T` any type | `T`: the largest or the smallest operand by [the order of `T`](#ordering-and-equality); `decimal` if any operand is |
| `nullIfEqual` | `{ left: T?, right: T? }`, `T` any type | `T?`, always nullable, with the type of `left`: an `integer` `left` stays `integer?` next to a `decimal` `right` |

`greatest` and `least` compare the expressions of one row, where the aggregates `max` and `min` compare the rows of a group: the later of two dates, the larger of plan and actual, and a value clamped to a range with `least(greatest(x, low), high)` ([`028_greatest_least.json`](samples/valid/028_greatest_least.json)). They are lifted, so the result is `null` when any operand is `null`; unlike `max` and `min` they do not skip it. To leave an operand out when it is `null`, give it a default with `coalesce`.

`nullIfEqual` is `null` when `left` equals `right` and `left` otherwise, so it reads a value that stands for "missing" as `null`: an empty string, a sentinel, a zero divisor. It is how a division avoids [failing on zero](#execution-errors): `divide` is lifted, so `divide(total, nullIfEqual(limit, 0))` is `null` where `limit` is zero, and `coalesce` over it gives a default. The same guard serves `integerDivide` and `modulo`, and there is no separate division operator for it ([`066_null_if_equal.json`](samples/valid/066_null_if_equal.json)). Null on any other condition is `if` with a `null` branch.

### Aggregates

```json
{ "operator": "sum", "type": <result type>, "over"?: "all" | <window>, "selector": <row expression>, "predicate"?: <row boolean> }
```

| Operator | Selector | Result |
|---|---|---|
| `count` | none | `integer` |
| `countDistinct` | any type | `integer`: the number of different values; `0` for no rows |
| `sum` | `integer` / `decimal` | type of the selector, non-null; `0` for no rows |
| `average` | `decimal`, `date`, `time`, `datetime` | `decimal` for numbers, otherwise the selector type |
| `min`, `max` | any type | type of the selector |
| `first`, `last` | any type; `orderBy` required | type of the selector: its value in the first or the last row |
| `median` | `decimal`, `date`, `time`, `datetime` | `decimal` for numbers, otherwise the selector type |
| `percentileContinuous` | `decimal`, `date`, `time`, `datetime`; `fraction` required | `decimal` for numbers, otherwise the selector type |
| `percentileDiscrete` | any type; `fraction` required | type of the selector |
| `mode` | any type | type of the selector: its most frequent value |
| `variancePopulation`, `standardDeviationPopulation` | `decimal` | `decimal` |
| `varianceSample`, `standardDeviationSample` | `decimal` | `decimal?`, always nullable |
| `covariancePopulation` | none; `left` and `right`: `decimal` | `decimal` |
| `covarianceSample`, `correlation` | none; `left` and `right`: `decimal` | `decimal?`, always nullable |
| `regressionSlope`, `regressionIntercept`, `regressionRSquared` | none; `y` and `x`: `decimal` | `decimal?`, always nullable |
| `concatAll` | `string`; `separator` and `orderBy` required, `distinct` optional | `string`, never null: the values joined in order; the empty string for no rows |
| `any`, `all` | none; `predicate` required | `boolean`. Over no rows, `any` is `false` and `all` is `true` |

- An aggregate runs over the current group in a grouped query and over every row after `where` in a plain one, as in SQL. Write `over: "all"` in a grouped query for a total over every row, e.g. a group's share of all revenue; `"group"` is never written. In a plain query `over` holds a [window](#windows) instead: the rows of the current row's partition, or a frame of them. A total query has no `over`.
- `predicate` filters the rows the aggregate sees: `count` with a predicate counts the matching rows. `count` without one counts every row.
- `countDistinct` counts the different values of its selector, e.g. the customers behind a group of orders: `{ "operator": "countDistinct", "type": { "name": "integer" }, "selector": <row expression> }`. The selector may have any type. Values are compared as `equal` compares them and `null` is not a value, so a column of `null`s counts `0`; like `count` it is never null, also in a total query. Strings that differ in case are different values: count `foldCase` of the string to ignore case. No other aggregate has a distinct form: several columns are told apart by a subquery with `distinctBy`, read by `count` ([`091_count_distinct.json`](samples/valid/091_count_distinct.json)).
- `null` values from the selector are skipped by `countDistinct`, `sum`, `average`, `min`, `max`, the statistical aggregates and `concatAll`.
- `concatAll` joins the strings of its rows into one, with `separator` between them, in the order of its own `orderBy`, which is written as for `first` and `last`: `{ "operator": "concatAll", "type": { "name": "string" }, "selector": …, "separator": { "type": { "name": "string" }, "value": ", " }, "orderBy": [ … ] }`. `separator` is a `string` literal or a `string` parameter, never a computed value. With `"distinct": true` each value is listed once; `false` is never written. Like `sum` it has a value over no rows, the empty string, so it is never null, also in a total query ([`097_concat_all.json`](samples/valid/097_concat_all.json)).
- A percentile takes a `fraction` from 0 to 1, as a `decimal` literal or a `decimal` parameter, never a computed value: `{ "operator": "percentileContinuous", "type": …, "selector": …, "fraction": { "type": { "name": "decimal" }, "value": "0.9" } }`. `median` is the continuous percentile of `0.5`. `percentileContinuous` interpolates between two values, so it takes the types `average` takes and a percentile of `integer` values is a `decimal`; `percentileDiscrete` and `mode` return one of the values and keep its type ([`093_statistics.json`](samples/valid/093_statistics.json)).
- A sample of one row has no variance, so `varianceSample` and `standardDeviationSample` are nullable wherever they are, also in a group.
- `covariancePopulation`, `covarianceSample` and `correlation` are statistics of two columns: `{ "operator": "correlation", "type": …, "left": <row expression>, "right": <row expression> }`. `left` and `right` take the place of `selector`; they are symmetric, so the names are those of `equal`. `predicate` and `over` are as for every aggregate. A row counts only when both values are non-null. `covariancePopulation` is typed as `variancePopulation` is, non-null in a plain or grouped query with two non-null operands and no `predicate`; the other two are nullable wherever they are, since one pair has neither and a column of one value has no correlation ([`095_covariance_and_correlation.json`](samples/valid/095_covariance_and_correlation.json)).
- `regressionSlope`, `regressionIntercept` and `regressionRSquared` describe the straight line that fits `y` to `x` best, by least squares: `{ "operator": "regressionSlope", "type": { "name": "decimal", "nullable": true }, "y": <row expression>, "x": <row expression> }`. `y` is the value explained and `x` the value it depends on; the line is not symmetric, so the operands are named, as those of `atan2` are. The slope is the change of `y` for one unit of `x`, the intercept is `y` where `x` is 0, and `regressionRSquared` is the share of the variance of `y` that the line explains, from 0 to 1. A value the line predicts is the intercept plus the slope times `x`. `x` is a number: for a trend over time it is `dateDiffDays` from a fixed date. A row counts only when both values are non-null, and the three are nullable wherever they are, since one pair has no line ([`096_linear_regression.json`](samples/valid/096_linear_regression.json)).
- `first` and `last` take their own `orderBy`, a list of `{ expression, direction }` items like [the query's](#orderby), each a row expression: `{ "operator": "first", "type": …, "selector": …, "orderBy": [ … ] }`. They sort the rows the aggregate sees and yield the selector's value in the first or the last of them, e.g. the total of each user's first order, or the date of the largest one ([`092_first_last.json`](samples/valid/092_first_last.json)). The value of that row is returned even when it is `null`; see [Aggregate evaluation](#aggregate-evaluation).
- `average`, `min`, `max`, `first`, `last`, `median`, the percentiles, `mode`, `variancePopulation` and `standardDeviationPopulation` are non-null in a plain or grouped query when they have no `predicate` and a non-null selector: a result row exists only when a row of the sources does, so every aggregate, over the group or over all rows, sees at least one, and a window always holds the current row. With a `predicate` or a nullable selector they are nullable, and in a total query they always are, since it returns its row even over no rows.

### Windows

In a plain query a function can read, for each row, a **window**: a set of rows related to that row, such as the earlier orders of the same user. The window is written on the function, as `over`:

```json
{ "operator": "sum", "type": { "name": "decimal" }, "selector": <row expression>,
  "over": { "partitionBy": [ <row expression>, … ],
            "orderBy": [ { "expression": <row expression>, "direction"?: "desc" }, … ],
            "frame": { "preceding"?: <rows>, "following"?: <rows> } } }
```

| Part | Meaning |
|---|---|
| `partitionBy` | The window holds the rows equal to the current row on every key. Without it, every row |
| `orderBy` | The order of those rows, written as [the query's `orderBy`](#orderby), with row expressions |
| `frame` | Of the ordered rows, those from `preceding` rows before the current row to `following` rows after it. Each is a number from 1, a non-null `integer` parameter, or `"all"` for every row on that side |
| `range` | Instead of `frame`: the rows whose sort key lies within a distance of the current row's key, from `preceding` below it to `following` above it. Each is a distance, written for the type of the key, or `"all"` |

Every part is optional, but a window names at least one: with none it would be every row, which is the absence of `over`.

- **Aggregates.** Every [aggregate](#aggregates) takes a window, and then runs over its rows instead of over all rows: a user's total next to each of their orders is `sum` with `"over": { "partitionBy": [ <user_id> ] }` ([`111_partition_totals.json`](samples/valid/111_partition_totals.json)). An aggregate's window has `orderBy` together with a `frame` or a `range`, or none of them. Without them it is the whole partition; with an order the frame is always stated, as rows or as a range of values, so there is no default frame to remember. `{ "preceding": "all" }` is a running total ([`112_running_totals.json`](samples/valid/112_running_totals.json)), `{ "preceding": 6 }` a moving window of seven rows, and `{ "preceding": 1, "following": 1 }` a row with its two neighbours ([`113_moving_averages.json`](samples/valid/113_moving_averages.json)).
- **The current row is always in its frame.** A side that is absent has no rows, so `0` is never written, an empty frame is rejected, and so is `"all"` on both sides, which is the whole partition. A window is therefore never empty, and an aggregate over one is typed exactly as it is over all rows: `average`, `min`, `max` and the aggregates typed like them are non-null with a non-null selector and no `predicate`.
- **A range of values.** A `frame` counts rows, which is wrong as soon as a period has no rows or several: twelve rows back is not twelve months back. A `range` measures along the sort key instead ([`114_range_frames.json`](samples/valid/114_range_frames.json)):

  ```json
  "over": { "partitionBy": [ <user_id> ],
            "orderBy": [ { "expression": <order_date> } ],
            "range": { "preceding": { "days": 29 } } }
  ```

  The window then has exactly one sort key, which declares a type that has distances, nullable or not:

  | Sort key | A distance |
  |---|---|
  | `integer` | a number from 1, or a non-null `integer` parameter |
  | `decimal` | the same, or a positive `decimal` literal, or a non-null `decimal` parameter |
  | `date` | `{ "days": n }` or `{ "months": n }` |
  | `datetime` | `{ "seconds": s }` or `{ "months": n }` |

  with `n` written as for an `integer` key and `s` as for a `decimal` key. A `string`, `boolean`, `uuid` or `time` key has no range: a time of day wraps around midnight. Like a frame, a range has at least one side, not `"all"` on both, and no distance of zero; a distance is never computed. The current row and the rows that share its key are always inside, so aggregates keep their types, and a running total over `{ "preceding": "all" }` is the same in every interpreter, where a frame of rows depends on the order of tied rows. Ranking functions and `previous` / `next` take no range.
- **Ranking and neighbouring rows.** These operators exist only with a window. They need its `orderBy` and take no `frame`:

| Operator | Properties | Result |
|---|---|---|
| `rowNumber` | none | `integer`: the position of the row in its partition, from 1 |
| `rank` | none | `integer`: the position of the first of the rows tied with it, so tied rows share a rank and a gap follows them |
| `denseRank` | none | `integer`: as `rank`, without gaps |
| `percentRank` | none | `decimal` from 0 to 1: (`rank` − 1) / (rows − 1) |
| `cumulativeDistribution` | none | `decimal` above 0 up to 1: the share of the partition's rows up to the row and the rows tied with it |
| `ntile` | `buckets` | `integer`: the bucket of the row, from 1, when the partition is cut into `buckets` parts of equal size |
| `previous`, `next` | `operand`; `offset` and `default` optional | the type of `operand`: its value `offset` rows before, or after, the current row |

```json
{ "operator": "previous", "type": { "name": "decimal" },
  "operand": { "source": "orders", "field": "total", "type": { "name": "decimal" } },
  "default": { "type": { "name": "integer" }, "value": 0 },
  "over": { "partitionBy": [ <user_id> ], "orderBy": [ { "expression": <ordered_at> }, { "expression": <id> } ] } }
```

- `previous` and `next` read `operand`, a row expression, in another row of the partition: the one before or after the current row, or `offset` rows away. `offset` is an `integer` literal from 2 or an `integer` parameter, never a computed value; one row away is the absence of `offset`. Where the partition has no such row the result is `default`, a non-null row expression of the operand's type, or `null` without one. So the result has the type `operand` declares, and is non-null exactly when there is a `default` and the operand is non-null ([`116_previous_next.json`](samples/valid/116_previous_next.json)).
- The ranking functions are never null: every row has a position. `buckets` is an `integer` literal from 1 or an `integer` parameter ([`115_ranking.json`](samples/valid/115_ranking.json)).
- **Where they may appear.** Window functions belong to projection context: the `select` and `orderBy` of a plain query, also as operands of other operators, e.g. `subtract(total, previous(total))`. Partition keys, sort keys, operands and aggregate bodies are row expressions, so window functions do not nest and do not read aggregates. A window never sorts the result; the query's `orderBy` does.
- **Filtering on a window function.** They are computed over the rows left by `where`, so a condition on one, such as the three largest orders of each user, belongs to a query that reads this one as a [subquery](#subqueries) ([`117_top_n_per_group.json`](samples/valid/117_top_n_per_group.json)).
- **Grouped rows.** A grouped query has no windows; `over` there is only `"all"`. A running total of monthly sums groups in a subquery and reads it with a plain query, whose windows then run over the grouped rows ([`118_running_total_of_monthly_sums.json`](samples/valid/118_running_total_of_monthly_sums.json)).

What each function computes is under [Window evaluation](#window-evaluation).

## Semantics

This section fixes what an interpreter computes, so that two conforming interpreters return the same rows for the same query, data and parameters. An **error** fails the whole query: no rows are returned.

### Evaluation

- **Sources and joins.** `from` yields the rows of its entity or subquery. Each join combines the rows so far with the joined source: `inner` keeps the pairs for which `on` is `true`; `left` also keeps every row so far that matched nothing, with `null` for the joined source's fields; `right` also keeps every joined row that matched nothing, with `null` for the fields of all earlier sources; `full` does both. `on` with the literal `true` is a cross join.
- **`where`** keeps the rows whose condition is `true`.
- **`groupBy`** partitions the rows by their keys, compared with `equal`: all `null` keys form one group, and `1` and `1.0` are the same `decimal` key. A group always has at least one row, so a grouped query over no rows returns no rows. **`having`** keeps the groups whose condition is `true`.
- **`select`** yields one row per row in a plain query and one row per group in a grouped query. **`aggregate`** yields exactly one row.
- **Window functions** are computed with `select` in a plain query, each over the rows left by `where`; see [Window evaluation](#window-evaluation).
- **`orderBy`** sorts by its keys in turn, by [the order of each type](#ordering-and-equality). Rows equal on every key come in an unspecified order.
- **`distinctBy`** then walks the sorted rows and drops each row equal, on the listed columns compared with `equal`, to a row before it. The rows kept stay in `orderBy` order.
- **`pagination`** skips `skip` rows, or none without `skip`, then returns at most `take` rows, or every row that is left without `take`.
- **Subqueries** behave as if each ran once, before the main query. Inline rows return one row for each row written, duplicates included. A subquery's result is an unordered collection: its `orderBy` only decides which rows its `pagination` and `distinctBy` keep, so a subquery has `orderBy` only together with one of them, and `pagination` only with `orderBy`.
- **Recursive subqueries.** Level 0 is the result of `seed`. Level n + 1 is the result of `next`, run with the subquery's name standing for the rows of level n, so `next` sees each row once. The result is the rows of every level, up to the first level that is empty. If level `maxDepth` + 1 would hold a row, the query fails.
- **Set operations** compare rows column by column with `equal`, so two `null`s are the same value, and `1` and `1.0` are. `unionAll` returns every row of every input: a row that one input returns twice and another three times is returned five times. `union` returns each distinct row of those once. `intersect` returns each distinct row that occurs in every input, and `except` each distinct row of the first input that occurs in no other. The result is unordered. Each input behaves as if it ran once, on its own.
- **Laziness.** An operation raises an error only if it is evaluated, and evaluation is lazy where it matters: `if` evaluates only the branch it takes, `coalesce` stops at its first non-`null` operand, `and` stops at the first `false` condition and `or` at the first `true`. So `if(equal(n, 0), 0, divide(x, n))` never divides by zero.
- **`greatest`** and **`least`** evaluate every operand and yield the largest or the smallest by [the order of their type](#ordering-and-equality), or `null` when any operand is `null`. Numbers compare by value, and with a `decimal` operand the result is a `decimal` whichever operand it comes from. Operands that are equal are the same value, so it does not matter which one is returned.
- **`nullIfEqual`** evaluates both operands and compares them with `equal`. It is `null` when they are equal and the value of `left` otherwise. Numbers compare by value, so `nullIfEqual(x, 0)` is `null` for every zero, `integer` or `decimal`; strings compare code point by code point. A `null` `left` gives `null`, and a `null` `right` leaves `left` as it is.

### Execution errors

A query fails at execution with an error when it:

- produces an `integer` outside the 64-bit range, or a `decimal` of magnitude 10²⁸ or more, in a result or in a step of an operator over a list, never in the partial sums of an aggregate (see [Integer and decimal arithmetic](#integer-and-decimal-arithmetic));
- divides by zero in `divide`, `integerDivide` or `modulo` (for `null` instead, divide by `nullIfEqual(divisor, 0)`);
- takes the `sqrt` of a negative number; the `asin` or `acos` of a number outside −1 to 1; the `atan2` of two zeros; the `ln`, `log10` or `log` of a number that is not positive; a `log` to a `base` that is not positive or is `1`; a `power` of zero to a negative `exponent`, or of a negative number to an `exponent` that is not a whole number;
- takes a `substring` with a `start` below 1 or a negative `length`, a `position` with a `start` below 1, a `splitPart` with an `index` of 0, or a `repeat` with a negative `count`;
- reads, with an `as…` operator, a string that is not written as a literal of the type;
- produces a `date` or `datetime` outside the years 0001–9999;
- builds a date or a time from a part outside its range, with `dateFromParts` or `timeFromParts`;
- computes, for a row, a `zone` that is not a [time zone name](#time-zones), or is run with such a `zone` parameter;
- is run with a regular expression parameter that is not a pattern of the dialect, or with a `group` parameter that is below 1 or names a group the pattern does not have;
- is run with a `fraction` parameter that is below 0 or above 1;
- is run with a frame count or a range distance parameter below 0, or an `offset` or `buckets` parameter below 1;
- produces, in a recursive subquery, a row deeper than `maxDepth`, or is run with a `maxDepth` parameter below 1;
- is run with a missing parameter, a parameter of the wrong type, `null` for a non-null parameter, a parameter value not written like a literal of its type (a `decimal` outside its range, a `datetime` not in UTC, and so on), or a `pagination` parameter below its minimum (`skip` < 0, `take` < 1).

### Integer and decimal arithmetic

- **`integer`** is a signed 64-bit integer, from −2⁶³ to 2⁶³ − 1. Any `integer` result outside that range is an error, including `sum`, `abs`, `round`, `truncate`, `floor` and `ceiling`. For an operator over a list and for an aggregate, which results count is fixed under *Operators over a list* and *Aggregates* below.
- **`decimal`** is an exact decimal number, never binary floating point: `0.1 + 0.2` equals `0.3`. Every value is m × 10⁻ˢ with an integer |m| < 10²⁸ and 0 ≤ s ≤ 28: at most 28 significant digits and 28 decimal places, which `System.Decimal` and every other decimal type of 28 digits or more holds exactly. A literal outside this range is rejected by the schema and a parameter outside it is an execution error, so literals and parameters are read exactly. A result that needs more digits is rounded half away from zero to the most decimal places that fit, so every interpreter computes the same result; a result of magnitude 10²⁸ or more is an error.
- **Mixed operands.** An `integer` operand of a `decimal` operation is converted exactly. Comparisons and `equal` between `integer` and `decimal` compare numeric values: `2` equals `2.0`.
- **`divide`** computes the exact quotient, rounded half away from zero to the decimal precision: `divide(1, 3)` is `0.3333333333333333333333333333` with 28 digits.
- **Operators over a list.** `add`, `subtract`, `multiply` and `divide` with more than two `values` go from left to right, one operation at a time: `add(a, b, c)` is `add(add(a, b), c)`, and likewise for the other three. Each step is a result of its own, with the type its two operands give: it is rounded to the decimal precision, and a step outside the range of its type is an [error](#execution-errors), even when a later step would bring the value back ([`021_operators_over_a_list.json`](samples/valid/021_operators_over_a_list.json)).
  - `divide(2, 3, 2)` is `divide(0.6666666666666666666666666667, 2)`, which is `0.3333333333333333333333333334`, where `divide(2, 6)` is `0.3333333333333333333333333333`.
  - `multiply(1.5, 0.0000000000000000000000000001, 3)` is `0.0000000000000000000000000006`: the first step, `0.00000000000000000000000000015`, has 29 decimal places and rounds to `0.0000000000000000000000000002`. Rounded only once, the product would be `0.0000000000000000000000000005`.
  - `add(9223372036854775807, 1, -1)` is an error, as its first step is beyond 64 bits, while `add(9223372036854775807, -1, 1)` is `9223372036854775807`. In `add(9223372036854775807, 1, 0.5)` the first step is still an `integer` addition and fails; a `decimal` operand widens only the steps from the one it takes part in.
  - So the order of the operands is part of the result, as it is for nested operators. A query that needs one rounding writes a single division, `divide(2, multiply(3, 2))`, or rounds explicitly with `round`.
- **Aggregates.** `sum`, `average` and the statistical aggregates are computed from the exact values of the rows they see, over a group, all rows or a window alike, and only their result is rounded and checked against its range. A partial sum is never a result: the rows of a group have no order, so a check on a running total would depend on the order in which an interpreter reads them.
  - `sum` of the `integer` values `9223372036854775807`, `1` and `-1` is `9223372036854775807`, whatever the order of the rows, where `add` of the same three operands fails at its first step. A `sum` is an error only when the sum itself is beyond 64 bits.
  - `average` of the `decimal` values `9000000000000000000000000000` and `9000000000000000000000000000` is `9000000000000000000000000000`, although their sum is beyond the range of `decimal`. Likewise a variance is computed from exact squares, which may need more digits than a `decimal` holds.
- **`integerDivide`** is the exact quotient truncated toward zero, and **`modulo`** is what is left, `left − right × integerDivide(left, right)`, which takes the sign of `left`. So `left = right × integerDivide(left, right) + modulo(left, right)`: `integerDivide(-7, 2)` is `-3` and `modulo(-7, 2)` is `-1`. Both take decimals as well ([`025_decimal_remainders.json`](samples/valid/025_decimal_remainders.json)):

  | `left` | `right` | `integerDivide` | `modulo` |
  |---|---|---|---|
  | `7.5` | `2` | `3` | `1.5` |
  | `-7.5` | `2` | `-3` | `-1.5` |
  | `7.5` | `-2` | `-3` | `1.5` |
  | `1` | `0.3` | `3` | `0.1` |
  | `19.95` | `0.05` | `399` | `0` |
  | `3` | `1.0000000000000000000000000001` | `2` | `0.9999999999999999999999999998` |

  - `integerDivide` is not `truncate(divide(…))`: `divide` rounds its quotient to the decimal precision first, which turns the `2.99…` of the last row into `3`. The quotient is truncated exactly, and it is an `integer` whatever the operands; one outside 64 bits is an error.
  - `modulo` is exact and never rounded: it is smaller in magnitude than `right` and has no more decimal places than the operands. `modulo(x, 1)` is the fractional part of `x`, and `equal(modulo(x, step), 0)` says that `x` is a multiple of `step`.
  - A remainder with the sign of the divisor, never negative for a positive `right`, is `modulo(add(modulo(x, y), y), y)`.
- **`floor`** and **`ceiling`** round toward −∞ and +∞. **`round`** rounds half away from zero: `round(2.5)` is `3` and `round(-2.5)` is `-3`. With `digits`, it rounds to that many decimal places, and a negative `digits` rounds to tens, hundreds and so on: `round(1234.5, -2)` is `1200`. Rounding to a whole number takes a `decimal`: `floor`, `ceiling`, and `round` and `truncate` without `digits`, reject an operand that declares `integer`, which they could not change, as `asString` rejects a `string`. An `integer` is used as it is, and with `digits` it is still rounded: `round(1250, -2)` is `1300` ([`023_whole_numbers.json`](samples/valid/023_whole_numbers.json)).
  - With `digits`, `round` and `truncate` keep the type of their operand, as `abs` does. A `decimal` stays a `decimal` whatever the digits: `round(1234.5, -2)` is the `decimal` `1200`. An `integer` stays an `integer`: rounding to tens or hundreds never leaves the integers, and `digits` of 0 or more leave it as it is. So `round(quantity, -1)` is a group key, a number of days, a `count` of `repeat`, without a second rounding ([`024_integer_bands.json`](samples/valid/024_integer_bands.json)).
  - The type does not depend on the value of `digits`, which may be computed. A `decimal` from an `integer` is `asDecimal`.
  - Like every `integer` result, a rounded integer outside 64 bits is an [execution error](#execution-errors): `round(9223372036854775807, -3)` would be `9223372036854776000`.
  - `"mode": "halfEven"` rounds a value exactly halfway to the neighbour whose last kept digit is even ("banker's rounding"), which has no upward bias over many values. `mode` is a name, like the `form` of `normalize`: it is never an expression, and it changes neither the type nor the nullability of `round`. Without `mode` the rule is half away from zero, which is never written ([`026_round_half_to_even.json`](samples/valid/026_round_half_to_even.json)):

    | Expression | half away from zero | `halfEven` |
    |---|---|---|
    | `round(2.5)` | `3` | `2` |
    | `round(3.5)` | `4` | `4` |
    | `round(-2.5)` | `-3` | `-2` |
    | `round(2.345, 2)` | `2.35` | `2.34` |
    | `round(2.355, 2)` | `2.36` | `2.36` |
    | `round(1250, -2)` | `1300` | `1200` |

  - Only a value exactly halfway is affected: `round(2.5000001)` is `3` under both rules. `truncate`, `floor` and `ceiling` have no midpoint and take no `mode`, and the rounding of every other `decimal` result (`divide`, powers, `average`, the statistics) stays half away from zero. Rounding to a step, such as five cents, is `multiply(round(divide(x, 0.05)), 0.05)` under either rule.
- **`truncate`** rounds toward zero, dropping digits: `truncate(2.7)` is `2` and `truncate(-2.7)` is `-2`, where `floor` gives `-3`. With `digits` it keeps that many decimal places, and a negative `digits` truncates to tens, hundreds and so on, as for `round`: `truncate(1234.567, 2)` is `1234.56` and `truncate(1299, -2)` is `1200`, an `integer` like its operand.
- **`abs`** is the absolute value, in the type of its operand: `abs(-3)` is the `integer` `3` and `abs(-2.5)` is `2.5`. The `integer` −2⁶³ has no absolute value in range, so `abs` of it is an error. **`sign`** is `-1` for a negative number, `0` for zero and `1` for a positive one, an `integer` whatever the type of its operand.

- **Powers, roots and logarithms** are always `decimal`, as `divide` is, also over `integer` operands: `power(2, 10)` is the `decimal` `1024`, which `round` turns into an `integer`. `power(x, y)` is x raised to y, `sqrt` the square root, `exp(x)` is e raised to x, `ln` the natural logarithm, `log10` the logarithm to base 10 and `log` the logarithm of `operand` to `base`.
  - **Exact.** Each result is the exact mathematical value, rounded as every `decimal` result is: half away from zero to the most decimal places that fit. A value that a `decimal` holds is therefore returned as it is: `power(1.5, 2)` is `2.25`, `power(2, -2)` is `0.25`, `sqrt(6.25)` is `2.5`, and `log10(1000)` and `log(8, 2)` are `3`. Every other result has the same digits in every interpreter: `sqrt(2)` is `1.414213562373095048801688724`, `exp(1)` is `2.718281828459045235360287471` and `ln(2)` is `0.6931471805599453094172321215`.
  - **Not floating point.** Binary floating point gives 15 to 17 of these digits, so an interpreter computes them in decimal arithmetic of higher precision, and not with the `double` functions of its database or runtime.
  - **`power`.** Any number to the `exponent` `0` is `1`, zero included. A negative `operand` takes only a whole `exponent`: `power(-2, 3)` is `-8`. `sqrt(x)` equals `power(x, 0.5)`, and other roots are fractional exponents too: `power(x, divide(1, 3))` is a cube root, up to the rounding of its exponent.
  - **Range.** A result of magnitude 10²⁸ or more is an error, as for every `decimal`: `exp(64)` fits and `exp(65)` does not. A result too small for 28 decimal places rounds to `0`: `exp(-100)` is `0`.
  - **Domain.** A square root of a negative number, a logarithm of a number that is not positive or to a `base` that is not positive or is `1`, zero to a negative `exponent`, and a negative number to an `exponent` that is not whole are [execution errors](#execution-errors), like division by zero. Guard the operand with `if`, `greatest` or `nullIfEqual`.
- **Trigonometry** follows the same rule as the powers: `sin`, `cos`, `tan`, `asin`, `acos`, `atan` and `atan2` are always `decimal`, lifted, and yield the exact mathematical value rounded half away from zero to the decimal precision, so every interpreter returns the same digits ([`030_trigonometry.json`](samples/valid/030_trigonometry.json)).
  - **Radians.** Angles are in radians. Degrees become radians with `multiply(x, divide(pi, 180))`, and radians degrees with `multiply(x, divide(180, pi))`.
  - **`pi`** has no operand: `{ "operator": "pi", "type": { "name": "decimal" } }`. It is π rounded to the decimal precision, `3.141592653589793238462643383`, not π itself, so `sin(pi)` is `0.0000000000000000000000000003` and not `0`, while `cos(pi)` is `-1`.
  - **`atan2`** takes `y` first, then `x`, and is lifted over both: `atan2(1, -1)` is `2.356194490192344928846982537`, three quarters of π, where `atan(divide(1, -1))` cannot tell the quadrant.
  - **Values.** `sin(1)` is `0.8414709848078965066525023216`, `cos(1)` is `0.5403023058681397174009366074`, `tan(1)` is `1.557407724654902230506974807`, `atan(1)` is `0.7853981633974483096156608458`, `asin(0.5)` is `0.5235987755982988730771072305` and `acos(0)` is `1.570796326794896619231321692`.
  - **Domain.** `asin` or `acos` of a number outside −1 to 1, and `atan2` of two zeros, are [execution errors](#execution-errors), as is a result of magnitude 10²⁸ or more.
  - **Large angles.** An interpreter reduces an angle with π to more digits than the result has: `sin` of 10²⁷ needs about 56.
  - The hyperbolic functions are compositions of `exp`, and a great-circle distance is composed from `sin`, `cos`, `asin` and `sqrt`.

### Strings

A string is a sequence of Unicode code points. `equal` compares code point by code point: it applies no case folding, Unicode normalization or trimming, so `"a"` and `"A"` differ, and so do `"a"` and `"a "`. Ordering, used by comparisons, `orderBy`, `min` / `max` and `greatest` / `least`, is lexicographic by code point, and a string sorts before every longer string it is a prefix of. `concat` joins its operands unchanged. `length` is the number of code points, so the empty string has length `0`, a character outside the Basic Multilingual Plane counts once (not as two UTF-16 code units), and a combining sequence counts each of its code points.

`upper` and `lower` apply the default case conversion of the Unicode Standard (`toUppercase` and `toLowercase`): the full mappings, those of `SpecialCasing.txt` included, and no locale. So:

- one code point may become several, and the length may change: `upper("straße")` is `"STRASSE"`;
- the context-sensitive rule for sigma applies: `lower("ΟΔΟΣ")` is `"οδος"`, with a final `ς`;
- no language-specific rule applies, so `upper("i")` is `"I"` and `lower("I")` is `"i"` in every query, whatever the locale of the interpreter or of its store (no Turkish dotless `ı`);
- a code point with no case mapping is kept as it is.

`foldCase` applies the default case folding of the Unicode Standard (`toCasefold`): the full mappings of `CaseFolding.txt` (statuses C and F), and no locale. Its result is a key under which strings that differ only in case are equal; it is not meant to be shown. So:

- `foldCase("Straße")` and `foldCase("STRASSE")` are both `"strasse"`, where `lower` gives `"straße"` and `"strasse"`: a code point may fold to several, and the length may change;
- every sigma folds to `σ`, so `foldCase("ΟΔΟΣ")` equals `foldCase("οδος")`, while `lower` keeps the final `ς` apart;
- no language-specific rule applies: `foldCase("I")` is `"i"` and the dotless `ı` stays `ı`, in every locale;
- folding a folded string changes nothing;
- folding does not normalize: `é` written as one code point and as `e` with a combining accent stay different; that is what `normalize` is for.

Equality stays code point by code point, and no operator takes a flag for case. To match, group or sort without regard to case, apply `foldCase` to both sides: `equal(foldCase(a), foldCase(b))`, `contains(foldCase(text), foldCase(search))`, a `groupBy` key or a sort key `foldCase(name)` ([`037_fold_case.json`](samples/valid/037_fold_case.json)). For a regular expression, fold the operand and write the pattern in its folded form: in lower case, with `ss` for `ß`.

`normalize` returns its operand in a normalization form of the Unicode Standard (Annex #15), so that the same text written with other code points becomes one string. `form` names the form and is always written:

| `form` | Result |
|---|---|
| `"NFC"` | canonical decomposition, then canonical composition: `e` followed by a combining acute accent becomes the one code point `é` |
| `"NFD"` | canonical decomposition: `é` becomes `e` and the combining accent, two code points |
| `"NFKC"` | compatibility decomposition, then canonical composition: also the ligature `ﬁ` becomes `fi`, a full-width `ｆ` becomes `f`, and `²` becomes `2` |
| `"NFKD"` | compatibility decomposition |

- The canonical forms change how a text is encoded, never what it shows or means. Text arrives in either, depending on the keyboard and the system it comes from, so text is compared in one form: `equal(normalize(a, "NFC"), normalize(b, "NFC"))`. The compatibility forms also drop differences of presentation (ligatures, width, superscripts, circled digits): they are for search keys, not for text that is shown.
- The length may change: `length` counts code points, so `length(normalize("é", "NFD"))` is `2`.
- Normalizing a normalized string changes nothing.
- `form` is a name, like the `kind` of a join: it is not an expression, and there is no default form.
- Case folding does not keep a string normalized. To ignore case as well, fold first and normalize after: `normalize(foldCase(x), "NFC")`, or `"NFKC"` for a search key ([`038_normalize.json`](samples/valid/038_normalize.json)). The Unicode definition of a canonical caseless match also decomposes before it folds, `normalize(foldCase(normalize(x, "NFD")), "NFD")`; the two differ only for text with the Greek iota subscript.

`removeDiacritics` returns its operand without its accents: the string is decomposed (`"NFD"`), every nonspacing mark (a code point of general category `Mn`) is dropped, and what is left is composed again (`"NFC"`). So:

- `removeDiacritics("Crème Brûlée")` is `"Creme Brulee"` and `"Việt Nam"` gives `"Viet Nam"`. It applies to every script that writes accents as marks: `"άλφα"` gives `"αλφα"`;
- a letter that is not a base letter with a mark is kept: `ø`, `ł`, `đ`, `æ` and `ß` have no decomposition, so `"Łódź"` gives `"Łodz"`. Nothing is transliterated to ASCII;
- every nonspacing mark goes, also where it is more than an accent: `й` becomes `и`, and the vowel points of Hebrew and Arabic, the tone marks of Thai and the virama of the Indic scripts are removed. The operator is meant for text in which a mark decorates a letter;
- the result is always in the form `"NFC"`, whatever the form of the operand, and removing diacritics twice changes nothing;
- case is kept, and no operator takes a flag for accents. For a search key that ignores case and accents, fold first: `removeDiacritics(foldCase(x))`; to ignore ligatures and width as well, normalize to `"NFKC"` in between ([`039_remove_diacritics.json`](samples/valid/039_remove_diacritics.json)).

`trimStart` removes the strings listed in `removables` from the start of `operand`, and `trimEnd` from its end. At each step it removes the longest removable that the string starts with (ends with), and it repeats until none matches; the rest of the string is kept as it is. `trim` does both: `trimStart`, then `trimEnd` of the result.

- A removable is a string of one or more code points, matched code point by code point, like `equal`: `trimStart("000120", ["0"])` is `"120"`, and `trimEnd("12.50 USD", [" USD", "0", "."])` is `"12.5"`.
- The longest match is taken first, so the result does not depend on the order of `removables`, and repeating one changes nothing: `trimStart("abab", ["a", "ab"])` is `""`, never `"bab"`.
- `removables` is always written, with at least one item: there is no default set, so a query says what it removes and every interpreter removes the same. To trim spaces pass `[" "]`; tabs, line breaks, the no-break space U+00A0 and any other white space are removed only if listed.
- An empty removable never matches and is ignored, so removables that are all empty remove nothing.
- A string made only of removables becomes the empty string, never `null`.
- A removable is never null: `trim` is lifted over `operand` only.

`substring` returns the code points of `operand` from position `start`, counted from 1, to the end of the string, or `length` of them when `length` is given. It never reads past the string:

- a `length` that runs past the end gives the rest of the string: `substring("hello", 4, 10)` is `"lo"`;
- a `start` past the end gives the empty string, as does a `length` of `0`: `substring("hello", 6)` and `substring("hello", 2, 0)` are `""`, never `null`;
- a `start` below 1 or a negative `length` is an [execution error](#execution-errors): there is no counting from the end;
- The result is `null` when `operand`, `start` or `length` is `null`.

So `substring(s, 1, n)` is the first `n` code points of `s`, or all of `s` when it is shorter. Positions are code points, as for `length`: a character outside the Basic Multilingual Plane is one position.

`replace` returns `operand` with every occurrence of `pattern` replaced by `replacement`.

- `pattern` is literal text, matched code point by code point like `equal`: no wildcards, and case and accents matter.
- Occurrences are found from the start of the string and do not overlap; the text put in is not searched again: `replace("aaa", "aa", "b")` is `"ba"`, and `replace("a", "a", "aa")` is `"aa"`.
- An empty `replacement` removes the occurrences. An empty `pattern` occurs nowhere, so the string is returned as it is, as an empty removable of `trim` removes nothing.
- The result is `null` when `operand`, `pattern` or `replacement` is `null`. Several patterns are replaced by nesting `replace`.

`position` is the position of the first occurrence of `pattern` in `operand`, counted in code points from 1, or `0` when there is none: `position("banana", "an")` is `2` and `position("banana", "x")` is `0`.

- With `start`, the search begins at that position: `position("banana", "an", 3)` is `4`. The result is still counted from the start of the string. A `start` past the end finds nothing; a `start` below 1 is an [execution error](#execution-errors), as for `substring`.
- An empty `pattern` is found where the search begins, so `position(s, "")` is `1`, in line with `contains`, which an empty pattern always satisfies.
- The result is never `null` for a string: `0` says that the pattern is absent, so `greaterThan(position(s, p), 0)` is `contains(s, p)`, and a `substring` from a position should first check that it is not `0`.

`splitPart` splits `operand` at every occurrence of `delimiter`, found as `replace` finds its pattern, and returns the part numbered `index`. A string with n occurrences has n + 1 parts, and a part may be empty.

- Parts are counted from 1, and from the end with a negative `index`: `splitPart("a-b-c", "-", 2)` is `"b"` and `splitPart("a-b-c", "-", -1)` is `"c"`.
- A part that does not exist is the empty string, never `null`: `splitPart("a-b-c", "-", 5)` is `""`, like the middle part of `"a--c"`. An `index` of `0` is an [execution error](#execution-errors).
- An empty `delimiter` occurs nowhere, so the string is one part.
- There is no list of parts as a value: each part is read with its own `splitPart`.

`padStart` adds repetitions of `fill` before `operand`, and `padEnd` after it, until the string has `length` code points: `padStart("7", 3, "0")` is `"007"`.

- The last repetition is cut to fit: `padStart("abc", 6, "xy")` is `"xyxabc"` and `padEnd("abc", 6, "xy")` is `"abcxyx"`.
- A string that already has `length` code points or more is returned as it is. Padding never cuts, so a `length` of zero or below changes nothing; a string is cut with `substring`.
- `fill` is always written, as `removables` of `trim` is: there is no default. An empty `fill` adds nothing.
- The result is `null` when `operand`, `length` or `fill` is `null`. A number is padded after `asString`: `padStart(asString(n), 5, "0")`.

`repeat` is `operand` written `count` times: `repeat("ab", 3)` is `"ababab"`, and a `count` of `0` gives the empty string. A negative `count` is an [execution error](#execution-errors).

`reverse` returns the code points of `operand` in the opposite order: `reverse("abc")` is `"cba"`. It works on code points, as `length` does, so a combining sequence is reversed too and its marks come out before their base character.

`concatWith` joins its operands with `separator` between them and leaves out the operands that are `null`: `concatWith(["Ann", null, "Lee"], " ")` is `"Ann Lee"`.

- It is never `null`: when every operand is `null` it is the empty string. `concat`, by contrast, is lifted and gives `null`.
- Only `null` is skipped. An empty string is an operand like any other, so `concatWith(["a", "", "b"], "-")` is `"a--b"`; `nullIfEqual(x, "")` leaves it out.
- `separator` is never null and may be the empty string.

`contains`, `startsWith` and `endsWith` test whether the code points of `pattern` occur in `operand` as one consecutive run: anywhere, at its start, or at its end.

- The match is code point by code point, like `equal`: case and accents matter, and nothing is normalized. For a match that ignores case, apply `foldCase` to both operands.
- `pattern` is literal text, not a pattern language: `%`, `_`, `*` and `\` stand for themselves, so a value from a user needs no escaping.
- An empty `pattern` matches every non-null `operand`, the empty string included.
- Either operand may be any string expression, and the result is `false` when either is `null` (see [Null semantics](#null-semantics)).

### Regular expressions

`matchesRegex`, `extractRegex` and `replaceRegex` take a regular expression as `pattern`. Its dialect is the part on which Perl, RE2, .NET, Java, JavaScript and Python agree, so an interpreter can hand a pattern to the engine it runs on, with a translation where that engine reads a construct differently.

| Construct | Meaning |
|---|---|
| a code point other than `\ ( ) [ ] { } * + ? ^ $ .` and the vertical bar | itself |
| `\` before one of those characters or `/` | that character itself: `\.`, `\*`, `\\`, `\/`. No other character is escaped this way |
| `.` | any code point except a line feed (U+000A) |
| `[abc]`, `[a-z0-9]`, `[^abc]` | one code point of the set or of a range, in code point order; after a leading `^`, one that is not in it. Inside a class, `\`, `]`, `[` and `^` are written with a backslash, and `-` stands for itself when it is escaped, first or last |
| `\d`, `\w`, `\s` | a digit `[0-9]`, a word character `[A-Za-z0-9_]`, white space (space, tab, line feed, carriage return, form feed, vertical tab). These are ASCII sets, also inside a class |
| `\D`, `\W`, `\S` | a code point that is not in `\d`, `\w`, `\s` |
| `\t`, `\n`, `\r` | tab, line feed, carriage return |
| `^`, `$` | the start and the end of the string and nothing else: there is no multiline mode, and `$` does not match before a final line break |
| `\b`, `\B` | a word boundary, between a `\w` and a code point that is not one or an end of the string; and a position that is not a boundary |
| `a` then the vertical bar then `b` | alternatives, tried from left to right |
| `( … )`, `(?: … )` | a group. `( … )` captures and is numbered from 1 by its opening parenthesis; `(?: … )` does not capture |
| `*`, `+`, `?`, `{n}`, `{n,}`, `{n,m}` | the preceding atom zero or more times, one or more, zero or one, exactly n, n or more, n to m. Greedy; lazy with a `?` after it |

- **Not in the dialect:** backreferences, lookahead and lookbehind, named groups, flags (matching is always case-sensitive; to ignore case, match a pattern in folded form against `foldCase` of the operand), possessive quantifiers and atomic groups, Unicode property classes, POSIX named classes, and code point escapes: a code point is written as itself. In JSON a backslash is written twice, so the pattern `\d+` is the string `"\\d+"`.
- **Matching** is by code point, and a pattern matches anywhere in the string unless it is anchored: `matchesRegex("cabd", "ab")` is `true`. The match is the leftmost one, and among the matches that start there, the one found by trying alternatives from left to right, a greedy quantifier with as many repetitions as possible first and a lazy one with as few. This is the rule of backtracking matchers, not the longest-match rule of POSIX: `extractRegex("ab", "a|ab")` is `"a"`.
- **`matchesRegex`** is `true` when the pattern matches, and `false` for a `null` operand.
- **`extractRegex`** returns the text of the first match or, with `group`, what that group captured in it: `extractRegex("ann@example.com", "@(.+)$", 1)` is `"example.com"`. It is `null` when the operand is `null`, when nothing matches, and when the group took no part in the match. A group inside a repetition holds its last repetition. A match can be the empty string, which is not `null`.
- **`replaceRegex`** replaces every match, found from left to right without overlap, by `replacement`: `replaceRegex("a  b   c", "\s+", " ")` is `"a b c"`. After an empty match the search moves on by one code point, so `replaceRegex("abc", "x*", "-")` is `"-a-b-c-"`. `replacement` is literal text, in which `$1` and `\1` stand for themselves; to rearrange parts of a string, extract them and `concat`.
- **`pattern` and `group` are never computed.** A pattern is a string literal or a string parameter, and a group an `integer` literal from 1 or an `integer` parameter: the whole match is the absence of `group`. So an interpreter checks both before it reads a row, and a pattern that is not one of the dialect, with parentheses that do not balance, a range or a `{n,m}` out of order, or a `group` the pattern does not have is an error whatever the data. The schema already rejects, in a literal pattern, every construct outside the dialect that can be told apart token by token (see [Validation](#validation)).
- The dialect has no backreferences or lookaround, so a pattern can be matched in time linear in the length of the string; an interpreter is free to use a backtracking engine.

### Ordering and equality

Every type is ordered, and the same order serves comparisons, `min` / `max`, `greatest` / `least` and `orderBy`.

| Type | Equality | Order |
|---|---|---|
| `integer`, `decimal` | numeric value | numeric |
| `string` | code points | lexicographic by code point |
| `boolean` | value | `false` before `true` |
| `date` | calendar day | chronological |
| `time` | time of day | chronological from `00:00:00` |
| `datetime` | instant | chronological by instant |
| `uuid` | value | lexicographic over the 32 hexadecimal digits in lower case, which is the order of the 16 bytes read as unsigned big-endian |

`null` equals `null` and sorts first in ascending order (see [Null semantics](#null-semantics)). A comparison treats `null` as a missing value rather than as the least one:

| `left` | `right` | `greaterThan`, `lessThan` | `greaterThanOrEqual`, `lessThanOrEqual` | `equal` |
|---|---|---|---|---|
| value | value | by the order of the type | by the order of the type | by value |
| `null` | value | `false` | `false` | `false` |
| value | `null` | `false` | `false` | `false` |
| `null` | `null` | `false` | `true` | `true` |

- Two `null`s are equal, so they are also "at least" and "at most" each other: `greaterThanOrEqual(a, b)` is `or(greaterThan(a, b), equal(a, b))`, and `and(lessThanOrEqual(a, b), greaterThanOrEqual(a, b))` is `equal(a, b)`, whatever the operands. An inclusive bound that is itself `null` keeps the rows whose value is `null`. See [`069_comparing_nullable_values.json`](samples/valid/069_comparing_nullable_values.json).
- One `null` makes every ordering comparison `false`, although `null` sorts first: `lessThan(price, 10)` does not match a row without a price. So `not(lessThan(a, b))` is not `greaterThanOrEqual(a, b)` when exactly one operand is `null`: both are `false`.
- In SQL, with two nullable operands, `greaterThanOrEqual(a, b)` is `a >= b OR (a IS NULL AND b IS NULL)`. The `uuid` order is not the one SQL Server uses for `uniqueidentifier`; an interpreter on such a database must still sort by this rule.

### Dates and times

- **`date`** follows the proleptic Gregorian calendar, from `0001-01-01` to `9999-12-31`: year 0000 is excluded, as `System.DateTime`, Python, PostgreSQL and SQL Server cannot store it. `dateAddDays` adds whole calendar days, and `dateDiffDays` is `left − right` in days.
- **`time`** is a time of day with microsecond precision, from `00:00:00` up to but excluding `24:00:00`. `timeAddSeconds` wraps around midnight: `23:00:00` plus 7200 seconds is `01:00:00`, and negative seconds go backwards. `timeDiffSeconds` is `left − right` in seconds without wrapping, so it is negative when `left` is earlier.
- **Months.** `dateAddMonths` and `datetimeAddMonths` add whole calendar months, backwards for a negative number: the month and the year move, and the day of the month is kept. When the resulting month is shorter, the day is clamped to its last day: `2024-01-31` plus 1 month is `2024-02-29`, and `2023-01-31` plus 1 month is `2023-02-28`. A `datetime` is moved in UTC and keeps its time of day; with a `zone` it is moved in the calendar of that [time zone](#time-zones) and keeps its local time of day.
  - Adding months is therefore not reversible, and not additive: `2024-01-31` plus 1 month, then minus 1 month, is `2024-01-29`, and adding 1 month twice gives `2024-03-29` where adding 2 months gives `2024-03-31`. To step through the ends of months, add to the first month: `dateAddMonths(d, n)` for n = 1, 2, 3.
  - A year is 12 months: `2024-02-29` plus 12 months is `2025-02-28`.
  - A result outside the years 0001–9999 is an [execution error](#execution-errors), as for every date.
- **Months between.** `dateDiffMonths` and `datetimeDiffMonths` count the whole months from `right` to `left`, as the inverse of adding months: when `left` is not earlier than `right`, the result is the largest `n` for which `right` plus `n` months, as `dateAddMonths` adds them, is not later than `left`. When `left` is earlier, it is the negative of the months from `left` to `right`, so swapping the operands only changes the sign.
  - A month is complete on the same day of the next month: from `2024-01-15`, `2024-02-14` is 0 months and `2024-02-15` is 1.
  - At the end of a month the clamping of `dateAddMonths` applies: from `2023-01-31`, `2023-02-28` is 1 month, since January 31 plus 1 month is February 28; in a leap year, `2024-02-28` is 0 months from `2024-01-31` and `2024-02-29` is 1.
  - So `dateDiffMonths(dateAddMonths(d, n), d)` is `n` for every `n`, negative too, and someone born on February 29 is a year older on February 28 of a common year.
  - For a `datetime` the time of day counts, in UTC or in the `zone`: from `2024-01-15T12:00:00Z`, `2024-02-15T11:59:59Z` is still 0 months.
- **`datetime`** is an instant with microsecond precision; every day has 86400 seconds. `datetimeAddSeconds` and `datetimeDiffSeconds` work on the instant, and `datetime` results are returned in UTC, written with `Z`.
- **From parts.** `dateFromParts`, `timeFromParts` and `datetimeFromParts` build a value from its parts, and are lifted over every part ([`059_dates_from_parts.json`](samples/valid/059_dates_from_parts.json)).
  - They are the inverse of the parts: `dateFromParts(year(d), month(d), day(d))` is `d`, and `datetimeFromParts(asDate(dt), asTime(dt))` is `dt`.
  - `second` is a `decimal` and carries the fraction, as the seconds of `timeAddSeconds` do: `timeFromParts(18, 30, 15.25)` is `18:30:15.25`. It is rounded to microseconds, half away from zero.
  - A part outside its range is an [execution error](#execution-errors), as `asDate` of `"2024-02-30"` is: `year` 1 to 9999, `month` 1 to 12, `day` 1 to the last day of that month, `hour` 0 to 23, `minute` 0 to 59, and `second` from 0 up to but excluding 60, also after rounding. Nothing is clamped and nothing rolls over into the next month, hour or day: `dateFromParts(2023, 2, 29)` and `timeFromParts(24, 0, 0)` fail, where `dateFromParts(2024, 2, 29)` is `2024-02-29`. To clamp a day, apply `least` to it.
  - Without a `zone`, `datetimeFromParts` never fails: every `date` and `time` give an instant in range. With one, see [Time zones](#time-zones). `datetimeFromParts(2024-01-31, 18:30:00)` is `2024-01-31T18:30:00Z`, and with midnight it is `asDatetime` of the date.
  - There is no `try` form: a date that may not exist is `tryAsDate` of its text.
- **Parts** are integers. A calendar part is read from a `date` or a `datetime`, a clock part from a `time` or a `datetime`; a `datetime` is read in UTC, as it is written, or with a `zone` in that [time zone](#time-zones). A `date` has no clock parts and a `time` no calendar parts, so the schema rejects `hour` of a `date`.

  | Operator | Value | Range |
  |---|---|---|
  | `year` | calendar year | 1–9999 |
  | `quarter` | quarter of the year: January to March is 1 | 1–4 |
  | `month` | month of the year | 1–12 |
  | `day` | day of the month | 1–31 |
  | `dayOfWeek` | ISO 8601 day of the week: Monday is 1, Sunday is 7 | 1–7 |
  | `dayOfYear` | day of the year: January 1 is 1 | 1–366 |
  | `week` | ISO 8601 week: weeks start on Monday, and week 1 is the one with the year's first Thursday | 1–53 |
  | `weekYear` | the ISO 8601 week-numbering year that `week` belongs to | 1–9999 |
  | `hour` | hour of the day | 0–23 |
  | `minute` | minute of the hour | 0–59 |
  | `second` | whole second of the minute, without its fraction | 0–59 |
  | `microsecond` | the fraction of the second in microseconds | 0–999999 |

  `week` goes with `weekYear`, not with `year`: the first days of January can belong to the last week of the previous week-numbering year, and the last days of December to week 1 of the next. `2024-12-30` is a Monday, so it has `year` 2024, `week` 1 and `weekYear` 2025; `2021-01-01` has `year` 2021, `week` 53 and `weekYear` 2020.
- **`startOf…`** returns the start of the period that contains its operand, in the operand's type, so the result is still a `groupBy` key, a sort key and an operand of the other date and time operators. A `datetime` is truncated in UTC, and its time of day becomes `00:00:00` for a period of a day or longer; with a `zone` the period is one of the local calendar, see [Time zones](#time-zones).

  | Operator | Result | `2024-08-15T18:30:15.25Z` gives |
  |---|---|---|
  | `startOfYear` | January 1 of the year | `2024-01-01T00:00:00Z` |
  | `startOfQuarter` | the first day of January, April, July or October | `2024-07-01T00:00:00Z` |
  | `startOfMonth` | the first day of the month | `2024-08-01T00:00:00Z` |
  | `startOfWeek` | the Monday on or before the day, as ISO 8601 and `dayOfWeek` | `2024-08-12T00:00:00Z` |
  | `startOfDay` | midnight of the day | `2024-08-15T00:00:00Z` |
  | `startOfHour` | minutes, seconds and the fraction set to zero | `2024-08-15T18:00:00Z` |
  | `startOfMinute` | seconds and the fraction set to zero | `2024-08-15T18:30:00Z` |
  | `startOfSecond` | the fraction set to zero | `2024-08-15T18:30:15Z` |

  Each operator takes only the types it can change: a `date` has no `startOfDay` or finer, and a `time` no `startOfDay` or longer. `startOfWeek` may fall in the previous month or year (`2025-01-01` gives `2024-12-30`); it never leaves the range of `date`, as `0001-01-01` is a Monday. To group by month, use `startOfMonth` as the key rather than `year` and `month`: the key stays a `date`.
- A number of seconds with more than 6 fractional digits is rounded to microseconds, half away from zero. Microseconds are the finest precision that PostgreSQL, MySQL, SQL Server, Python, .NET and Java all hold exactly.

### Time zones

A `datetime` is an instant and has no time zone of its own. A zone is given to the operator that reads a calendar date or a time of day from the instant: without `zone` the operator reads the instant in UTC, as it is written, and with `zone` in the local time of that zone ([`052_local_dates_and_times.json`](samples/valid/052_local_dates_and_times.json)).

```json
{ "operator": "asDate", "type": { "name": "date" },
  "operand": { "source": "orders", "field": "ordered_at", "type": { "name": "datetime" } },
  "zone": { "type": { "name": "string" }, "value": "Europe/Moscow" } }
```

- **Operators.** `asDate` and `asTime` of a `datetime` take a `zone` and give the local day and the local time of day. The parts of a `datetime` take one too, and are then the parts of that local day and time: `year`, `quarter`, `month`, `day`, `dayOfWeek`, `dayOfYear`, `week`, `weekYear`, `hour`, `minute` and `second` ([`054_local_date_parts.json`](samples/valid/054_local_date_parts.json)).
  - A `zone` is only for a `datetime`. A `date`, a `time`, and a string that spells one have no zone to be read in, so `year` of a `date`, `hour` of a `time` and `asDate` of a string take none.
  - `microsecond` takes none: an offset from UTC is a whole number of seconds, so the fraction of a second is the same in every zone.
  - `year(dt, zone)` is `year(asDate(dt, zone))`, and likewise for every part: the shorter form reads the same local date and time.
  - `startOfYear`, `startOfQuarter`, `startOfMonth`, `startOfWeek`, `startOfDay`, `startOfHour` and `startOfMinute` of a `datetime` take one and give the start of a local period, as described below.
  - `asDatetime` of a `date` and `datetimeFromParts` take one and go the other way, from a local date and time to an instant, as described below.
  - `datetimeAddMonths` and `datetimeDiffMonths` take one and work in the local calendar, as described below.
  - No other operator takes a zone. Seconds are added to the instant and counted between instants, instants compare and sort the same in every zone, and a `datetime` literal, parameter and result are in UTC.
- **`zone` is a `string` expression**, an operand like any other: a literal, a parameter, or a value of the row, such as a column that holds the zone of a user or of a store. One query can then cut each row by its own local day. The operator is lifted over it: a `null` zone gives `null`, and the result is nullable exactly when the `datetime` or the zone is.
- **Names.** A zone is named as the [IANA time zone database](https://www.iana.org/time-zones) names it: `Europe/Moscow`, `America/New_York`, `Asia/Kolkata`. The schema lists the names a literal zone may hold ([`tools/time_zones.txt`](tools/time_zones.txt), 444 names from release 2026e of the database):
  - the current name of every zone, at least one for each country: the zones of the database's `zone.tab`;
  - the fixed offsets `Etc/GMT+12` to `Etc/GMT-14`, a whole number of hours each. Their sign is reversed, as in POSIX: `Etc/GMT-3` is three hours ahead of UTC.

  A name is matched exactly, letter case included, so a literal zone that is not in the list is rejected by the schema: a zone that does not exist (`Europe/Atlantis`), an older name the database keeps as a link (`US/Eastern` for `America/New_York`, `Asia/Calcutta` for `Asia/Kolkata`), an abbreviation (`MSK`, `EST`), which does not name one zone, and an offset (`+03:00`), which says nothing about daylight saving time.
- **UTC is the absence of `zone`.** A default is never written, so the list has no name for UTC: `UTC`, `Etc/UTC`, `GMT` and the others are rejected as literals.
- **Parameters and computed zones** are checked by the interpreter, since the schema sees no value: a parameter when it is bound, and a zone computed for a row when the row is read, where a value that is not a zone is an [execution error](#execution-errors). A name of the list is accepted by every interpreter, and so is `UTC`, which reads the instant as no zone does; whether another name is accepted is [not specified](#not-specified-yet).
- **Local time.** The local time of an instant is the instant shifted by the offset from UTC that the database gives the zone at that instant, daylight saving time included. Every instant has exactly one local time in a zone, so reading it cannot fail, except at the two ends of the range of dates: a local date outside the years 0001–9999 is an [execution error](#execution-errors), as for every date.

  | `2024-03-31T22:30:00Z` in | `asDate` | `asTime` |
  |---|---|---|
  | no zone (UTC) | `2024-03-31` | `22:30:00` |
  | `Europe/Moscow` | `2024-04-01` | `01:30:00` |
  | `America/New_York` | `2024-03-31` | `18:30:00` |
  | `Asia/Kathmandu` | `2024-04-01` | `04:15:00` |

  In `Europe/Moscow` that instant has `month` 4, `day` 1, `dayOfWeek` 1 and `hour` 1, where in UTC it has `month` 3, `day` 31, `dayOfWeek` 7 and `hour` 22; in `Asia/Kathmandu` its `minute` is 15. New York is 4 hours behind UTC on that day and 5 hours behind in January, so a fixed shift with `datetimeAddSeconds` does not give a local time: the offset of a zone changes with daylight saving time, and has changed over the years.
- **Local periods.** With a `zone`, `startOf…` gives the first instant of the period of the local calendar or clock that contains its operand: the earliest instant whose local date and time fall in the same local year, quarter, month, week, day, hour or minute ([`055_local_periods.json`](samples/valid/055_local_periods.json)). The result is a `datetime`, an instant like any other, so it is a group key and a bound for a filter on instants. Its local day is `asDate` of it with the same zone.

  | Operator | `2024-08-15T18:30:15.25Z` in `Europe/Moscow`, where it is `21:30:15.25` | in `Asia/Kathmandu`, where it is `00:15:15.25` on August 16 |
  |---|---|---|
  | `startOfYear` | `2023-12-31T21:00:00Z` | `2023-12-31T18:15:00Z` |
  | `startOfQuarter` | `2024-06-30T21:00:00Z` | `2024-06-30T18:15:00Z` |
  | `startOfMonth` | `2024-07-31T21:00:00Z` | `2024-07-31T18:15:00Z` |
  | `startOfWeek` | `2024-08-11T21:00:00Z` | `2024-08-11T18:15:00Z` |
  | `startOfDay` | `2024-08-14T21:00:00Z` | `2024-08-15T18:15:00Z` |
  | `startOfHour` | `2024-08-15T18:00:00Z` | `2024-08-15T18:15:00Z` |
  | `startOfMinute` | `2024-08-15T18:30:00Z` | `2024-08-15T18:30:00Z` |

  - Two instants have the same `startOfDay` in a zone exactly when they fall on the same local day, and likewise for every period. So grouping by the start of a local period groups by the local period.
  - A local day is not always 24 hours long. In `America/New_York` the day `2024-03-10` starts at `2024-03-10T05:00:00Z` and the next one at `2024-03-11T04:00:00Z`: clocks are set forward that night, and the day has 23 hours. `2024-11-03` has 25.
  - Where clocks are set forward at midnight, the day starts at the first time that exists: in `Africa/Cairo`, `2024-04-26` starts at `01:00` local time, which is `2024-04-25T22:00:00Z`.
  - Where clocks are set back, an hour of local time passes twice, and both passes are the same local hour. In `Europe/Berlin`, `2024-10-27T00:30:00Z` and `2024-10-27T01:30:00Z` both read `02:30`, and `startOfHour` of both is `2024-10-27T00:00:00Z`: that local hour lasts two hours.
  - `startOfSecond` takes no zone: a second starts at the same instant in every zone.
- **From a local date and time to an instant.** `datetimeFromParts` with a `zone` gives the instant at which the clocks of the zone read that date and time, and `asDatetime` of a `date` with a `zone` gives the first instant of that local day ([`056_local_times_as_instants.json`](samples/valid/056_local_times_as_instants.json)). Clocks that are set forward or back make some local times occur never or twice, and one rule covers both: the result is **the first instant at which the local date and time are the given ones or later**.

  | In `America/New_York` | `date`, `time` | Result |
  |---|---|---|
  | a time that occurs once | `2024-01-31`, `18:30:00` | `2024-01-31T23:30:00Z` |
  | a time that occurs twice: clocks are set back from 02:00 to 01:00 | `2024-11-03`, `01:30:00` | `2024-11-03T05:30:00Z`, the first of the two |
  | a time that never occurs: clocks are set forward from 02:00 to 03:00 | `2024-03-10`, `02:30:00` | `2024-03-10T07:00:00Z`, when the clocks read `03:00:00` |

  - A later local time never gives an earlier instant, so a bound built this way cuts the timeline at one point. The rows of a local day are those from `asDatetime(day, zone)` up to but excluding `asDatetime(dateAddDays(day, 1), zone)`.
  - `asDatetime(d, zone)` is `datetimeFromParts(d, 00:00:00, zone)`, and `asDatetime(asDate(dt, zone), zone)` equals `startOfDay(dt, zone)`.
  - `datetimeFromParts(asDate(dt, zone), asTime(dt, zone), zone)` is `dt` again, except for an instant in the second pass of a repeated time, which gives the instant of the first pass.
  - The same local time on another day is built from parts, `datetimeFromParts(dateAddDays(asDate(dt, zone), 1), asTime(dt, zone), zone)`. Adding 86400 seconds gives another local time on a day when the clocks change.
  - A local day that a zone skipped altogether gives the first instant after it. `Pacific/Apia` had no `2011-12-30`, and `asDatetime` of that date there is `2011-12-30T10:00:00Z`, the start of December 31.
  - A result outside the years 0001–9999 is an [execution error](#execution-errors), as for every `datetime`: midnight of `0001-01-01` in a zone ahead of UTC is before the first instant.
- **Months in a local calendar.** `datetimeAddMonths` with a `zone` moves the local date by whole months, clamped to the end of the month as always, keeps the local time of day, and gives the instant of that local date and time by the rule above ([`057_months_in_a_local_calendar.json`](samples/valid/057_months_in_a_local_calendar.json)). It is `datetimeFromParts(dateAddMonths(asDate(dt, zone), n), asTime(dt, zone), zone)`. `datetimeDiffMonths` with a `zone` is its inverse: the whole months from `right` to `left` as `datetimeAddMonths` adds them in that zone.

  | Expression | In UTC | With the `zone` |
  |---|---|---|
  | `datetimeAddMonths(2024-02-15T17:00:00Z, 1)`, noon in `America/New_York` | `2024-03-15T17:00:00Z`, 13:00 there | `2024-03-15T16:00:00Z`, noon again |
  | `datetimeAddMonths(2024-03-30T22:00:00Z, 1)`, March 31 in `Europe/Moscow` | `2024-04-30T22:00:00Z` | `2024-04-29T22:00:00Z`: the local day is clamped to April 30 |
  | `datetimeDiffMonths(2024-03-15T16:30:00Z, 2024-02-15T17:00:00Z)` in `America/New_York` | 0 | 1: from noon to half past noon a month later |

  - The time of day that is kept is the local one, so a monthly renewal stays at the same local time when the clocks change in between.
  - Where the local time does not exist on the resulting day, the rule above applies: `2024-02-10T07:30:00Z` is 02:30 in `America/New_York`, and one month later is `2024-03-10T07:00:00Z`, when the clocks there jump from 02:00 to 03:00.
  - A `date` has no zone: `dateAddMonths` and `dateDiffMonths` take none, and the whole months between two local days are `dateDiffMonths` of `asDate` of each instant with the zone.
- **Local values are ordinary values.** `asDate(dt, zone)` is a `date` and `asTime(dt, zone)` a `time`, so they are group keys, sort keys and operands like any other: revenue by local business day groups by `asDate` with a zone, and "before 18:00 local time" compares `asTime` with a `time` literal. The instant itself is unchanged. Comparison, `min` / `max` and `datetimeDiffSeconds` of `datetime`s never depend on a zone, and `datetime` results are returned in UTC.
- **The database.** The schema fixes the names; the rules of each zone come from the release of the database an interpreter uses, and which one is [not specified](#not-specified-yet). Two interpreters give the same local time wherever their releases have the same rules for the zone at that instant.

### Conversion results

`asString` writes a value the way a literal of its type is written, in the one spelling of [Types](#types). The text is therefore the same in every interpreter, whatever its locale, and reading it back as a literal gives the value again.

| Type | Text | Example |
|---|---|---|
| `integer` | decimal digits, `-` before a negative number; no `+`, leading zeros or separators | `-42` |
| `decimal` | as a `decimal` literal: no exponent, no trailing zeros in the fraction, no `-0`, and no point for a whole number | `19.9`, `0.125`, `1200` |
| `boolean` | `true` or `false` | `true` |
| `date` | `YYYY-MM-DD`, the year in four digits | `0987-01-31` |
| `time` | `hh:mm:ss`, followed by the fraction only when it is not zero, without trailing zeros | `18:30:00`, `18:30:00.125` |
| `datetime` | the date, `T`, the time, `Z` | `2024-01-31T18:30:00Z` |
| `uuid` | 8-4-4-4-12 hexadecimal digits in lower case | `3f2a6c1e-8b4d-4e2a-9c1f-1a2b3c4d5e6f` |

- A `decimal` is written by its value, not by how it was computed: `asString(divide(1, 8))` is `0.125`, `asString` of `19.90` is `19.9`, and a `decimal` that is a whole number reads like an `integer`. `round` before the conversion limits the decimal places; nothing adds trailing zeros.
- `null` stays `null`, never the text `null`: the result is nullable exactly when the operand is, and `coalesce` gives a text for it.
- Display formats (thousands separators, month names, a local time zone) are left to the client.

`asDate` and `asTime` read a `datetime` in UTC, as it is written: for `2024-01-31T23:30:00Z` they give `2024-01-31` and `23:30:00`. With a `zone` they read it in that [time zone](#time-zones): in `Asia/Tokyo` the same instant is `2024-02-01` and `08:30:00`. `asDatetime` gives midnight UTC of a `date`: `2024-01-31T00:00:00Z`. So `asDatetime(asDate(dt))` equals `startOfDay(dt)`, in UTC and, with the same `zone` on all three, in that zone; a `datetime` is grouped or joined by its day with `asDate`, and a `date` and a `time` are combined into an instant with `datetimeFromParts(d, t)`.

`as…` of a string and `tryAs…` read exactly the text that `asString` writes for the type, the one spelling in the table above, and nothing else:

- an `integer` within 64 bits and a `decimal` within its 28 digits; a real calendar `date` from year 0001; a `datetime` in UTC with `Z`; a `uuid` in lower case;
- no surrounding spaces, no `+`, no leading zeros, no trailing zeros in a fraction, no exponent, no other letter case: ` 12`, `+5`, `007`, `1.50`, `1e3`, `TRUE`, `2024-1-5`, `2024-02-30`, `18:30`, `18:30:00.500` and `2024-01-31T18:30:00+00:00` are not read. This is the rule a [parameter](#parameters) value follows;
- the empty string is not a literal of any of these types.

So `asDecimal(asString(x))` is `x`, and `asString(asDecimal(s))` is `s` for every text that is read. Text in a wider format is cleaned first, e.g. with `trim`; a postal code such as `01234` is not an `integer` literal and stays a string. `as…` of any other text is an [execution error](#execution-errors), and of `null` is `null`. `tryAs…` gives `null` in both cases and never fails, so `equal(tryAsInteger(s), null)` finds the rows that hold something else.

### Aggregate evaluation

An aggregate sees the rows of its group, every row left by `where` (in a plain or total query, or with `over: "all"`), or the rows of its [window](#window-evaluation), and of those only the rows for which its `predicate` is `true`.

| Operator | Value | With no rows, or only `null` values |
|---|---|---|
| `count` | number of rows | `0` |
| `countDistinct` | number of different non-`null` values, compared with `equal` | `0` |
| `sum` | exact sum of the non-`null` values, the same in any order of the rows; an `integer` sum beyond 64 bits is an error, a partial sum never is | `0` |
| `average` | mean of the non-`null` values. Numbers: `sum` divided as by `divide`. `date`: mean day, rounded to the nearest whole day. `time`: mean of the times as seconds since midnight, without wrapping. `datetime`: mean instant, returned in UTC. `time` and `datetime` round to the nearest microsecond. A mean exactly halfway between two days, or two microseconds, is the later one | `null` |
| `min`, `max` | least and greatest non-`null` value by [the order of its type](#ordering-and-equality) | `null` |
| `first`, `last` | the selector's value in the first, or the last, of the rows sorted by the aggregate's `orderBy` | `null` |
| `median` | the middle of the non-`null` values in [their order](#ordering-and-equality): the middle one when their number is odd, otherwise the mean of the two middle ones, computed as `average` computes it | `null` |
| `percentileContinuous` | the value at position `fraction` × (n − 1), counted from 0, among the n non-`null` values in order, interpolated linearly between the two values next to that position | `null` |
| `percentileDiscrete` | the value number ⌈`fraction` × n⌉, counted from 1, among the n non-`null` values in order; the first value for the fraction `0`. It is the first value at or below which at least that fraction of the values lies | `null` |
| `mode` | the non-`null` value that occurs most often, compared with `equal`; among several, the least by the order of the type | `null` |
| `variancePopulation` | the mean of the squared differences between the non-`null` values and their mean; `0` for one value | `null` |
| `varianceSample` | the sum of those squared differences divided by n − 1 | `null`, also with one value |
| `standardDeviationPopulation`, `standardDeviationSample` | the square root of the variance of the same name | `null`; the sample form also with one value |
| `covariancePopulation` | over the pairs of non-`null` values, the mean of (x − x̄)(y − ȳ); `0` for one pair | `null` |
| `covarianceSample` | the sum of those products divided by n − 1 | `null`, also with one pair |
| `correlation` | Pearson's coefficient: the covariance divided by the product of the two standard deviations, from −1 to 1 | `null`, also with one pair, and when either column has the same value in every pair |
| `regressionSlope` | over the pairs of non-`null` values, the slope of the least-squares line of y on x: the population covariance divided by the population variance of x | `null`, also with one pair, and when x has the same value in every pair |
| `regressionIntercept` | y of that line where x is 0: ȳ − slope × x̄ | `null`, in the same cases |
| `regressionRSquared` | the share of the variance of y that the line explains: the squared covariance divided by the product of the two variances, from 0 to 1; `1` when y has the same value in every pair | `null`, in the same cases |
| `concatAll` | the non-`null` values, in the order of the aggregate's `orderBy`, with `separator` between them | the empty string |
| `any` | `true` when some row satisfies the predicate | `false` |
| `all` | `true` when every row satisfies the predicate | `true` |

`sum`, `average` and the statistical aggregates are computed from exact values and rounded once, as `divide` and `sqrt` are, and only their result is checked against its range, so every interpreter returns the same digits whatever the order in which it reads the rows (see [Integer and decimal arithmetic](#integer-and-decimal-arithmetic)).

- Over the values `1`, `2`, `3`, `4`: `median` is `2.5`; `percentileContinuous` is `3.7` for the fraction `0.9`, `1` for `0` and `4` for `1`; `percentileDiscrete` is `2` for `0.5` and `4` for `0.9`; `variancePopulation` is `1.25` and `varianceSample` is `1.666666666666666666666666667`; `standardDeviationPopulation` is `1.118033988749894848204586834` and `standardDeviationSample` is `1.290994448735805628393088467`.
- A date and an instant have no zero, so a temporal mean is never rounded "away from zero", which would depend on the day an interpreter counts from: a value exactly halfway between two days, or two microseconds, is the later one. The mean of `1969-12-30` and `1969-12-31` is `1969-12-31`, as the mean of `2024-01-01` and `2024-01-02` is `2024-01-02`. A number of seconds is still rounded half away from zero, as every number is. See [`094_temporal_averages.json`](samples/valid/094_temporal_averages.json).
- `median` and `percentileContinuous` over a `date`, a `time` or a `datetime` interpolate as `average` averages: in days, rounded to the nearest whole day, and in seconds, rounded to the nearest microsecond, with a value exactly halfway going to the later one. The median of `2024-01-01` and `2024-01-04` is `2024-01-03`.
- `percentileDiscrete` and `mode` return a value that occurs in the rows, so they exist for every type. The `fraction` is one value for the whole aggregate; bound to a parameter outside 0 to 1 it is an [execution error](#execution-errors).
- A standard deviation is the square root of the exact variance, not of its rounded value.
- The statistics of two columns read **pairs**: a row counts only when `left` and `right` are both non-`null` and its `predicate` is `true`, and x̄ and ȳ are the means over those rows. Over the pairs (1, 2), (2, 4), (3, 5), (4, 9): `covariancePopulation` is `2.75`, `covarianceSample` is `3.666666666666666666666666667` and `correlation` is `0.9647638212377321361920414832`. `covariancePopulation(x, x)` equals `variancePopulation(x)`. A correlation is computed exactly and rounded once, so it never falls outside −1 to 1.
- The regression aggregates read the same pairs, with x as `x` and y as `y`. Over the pairs (1, 2), (2, 4), (3, 5), (4, 9): `regressionSlope` is `2.2`, `regressionIntercept` is `-0.5` and `regressionRSquared` is `0.9307692307692307692307692308`; the line predicts `8.3` at x = 4. Each is computed from exact values and rounded once: the intercept is not computed from the rounded slope, and `regressionRSquared` is not the square of the rounded `correlation`, so the last digit may differ from a result composed by hand. Over (1, 3), (2, 3), (3, 3) the line is flat and fits exactly: the slope is `0`, the intercept `3` and `regressionRSquared` `1`, while `correlation` is `null`. Over (1, 2), (1, 5) no line is defined and all three are `null`.

`first` and `last` sort the rows they see, after `predicate`, by their own `orderBy`: its keys apply in turn, each by [the order of its type](#ordering-and-equality) with `null` first in ascending order, exactly as the query's `orderBy` sorts.

- The result is the selector's value in the first row (`first`) or the last (`last`), whether or not that value is `null`. Unlike `min` and `max` they pick a row rather than a value, so two of them with the same `orderBy` and `predicate` read the same row, e.g. the id and the total of the latest order. To take the first non-`null` value instead, exclude the other rows with `predicate`.
- Rows equal on every key come in an unspecified order, so which of them is first or last is unspecified too. End the keys with one that identifies a row, such as an `id`; the schema cannot check this, as for `pagination`.
- The order belongs to the aggregate: it does not sort the result, and each `first` or `last` of a query may have its own.

`concatAll` sorts the rows it sees by its own `orderBy`, as `first` and `last` do, skips the rows whose value is `null`, and joins the values that remain with `separator` between them.

- With `"distinct": true`, a value equal to one before it in that order is dropped, so each value appears once, at its first position.
- Rows equal on every key come in an unspecified order, and so do their values. To list values in their own order, sort by the selector: equal values are interchangeable, so the result is then the same in every interpreter. Otherwise end the keys with one that identifies a row.
- An empty string is a value like any other and is joined in; only `null` is skipped, as by `concatWith`.

### Window evaluation

Window functions are computed once the rows of a plain query are known: after `where`, and before `orderBy`, `distinctBy` and `pagination`. For each row, its window is found in three steps:

- **Partition.** The rows whose `partitionBy` keys all equal the row's, compared with `equal`: `null` keys are equal to each other, and `1` and `1.0` are the same key. Without `partitionBy` it is every row.
- **Order.** The partition sorted by the window's `orderBy`, exactly as the query's `orderBy` sorts: its keys in turn, each by [the order of its type](#ordering-and-equality), with `null` first in ascending order. Rows equal on every key are **peers**.
- **Frame.** The current row, up to `preceding` rows before it and up to `following` rows after it in that order: a frame stops at the ends of the partition. `"all"` is every row on that side.
- **Range.** With `range` in place of `frame`, a row of the partition is in the window when its sort key `k` lies within the distances of the current row's key `c`: `c − preceding ≤ k ≤ c + following` for an ascending key, both bounds included, and with a side absent `k = c` on that side. With `"direction": "desc"`, `preceding` reaches towards greater values. So the current row and all its peers are always inside, and the window does not depend on the order of peers.
  - Days and seconds are added as `dateAddDays` and `datetimeAddSeconds` add them, and months as `dateAddMonths` and `datetimeAddMonths` do, with the day clamped to the end of the month: a row is within `{ "months": n }` before when its key is not before the current key minus `n` months.
  - A row whose key is `null` has the rows of its partition whose key is `null` as its window, and is in the window of no other row.
  - A bound that falls outside the type (before `0001-01-01`, beyond 64 bits) is not an error: that side reaches the end of the partition. A bound is only compared, never returned.

An aggregate over a window is evaluated as under [Aggregate evaluation](#aggregate-evaluation), over the rows of the frame, or of the whole partition when the window has none. Its `predicate` filters those rows and does not move the frame: a frame of seven rows with a predicate aggregates at most seven. `first`, `last` and `concatAll` still sort the rows they see by their own `orderBy`; the window's order only places the frame.

| Operator | Value, in a partition of n rows |
|---|---|
| `rowNumber` | the position of the row in its ordered partition, counted from 1 |
| `rank` | 1 plus the number of rows that come before the row and are not its peers |
| `denseRank` | 1 plus the number of groups of peers that come before the row's own |
| `percentRank` | (`rank` − 1) divided by (n − 1); `0` when n is 1 |
| `cumulativeDistribution` | the number of rows that come before the row or are its peers, itself included, divided by n |
| `ntile` | the rows, in order, fill buckets numbered from 1 to `buckets`, each of ⌊n / `buckets`⌋ rows and the first n mod `buckets` of them of one more; the value is the number of the row's bucket. With more buckets than rows, the rows are numbered from 1 to n |
| `previous` | `operand` evaluated in the row `offset` positions before the current row in its ordered partition; one position without `offset` |
| `next` | the same, `offset` positions after it |

- `percentRank` and `cumulativeDistribution` divide as `divide` does: exactly, rounded once.
- Where the partition has no row at that position, `previous` and `next` yield `default`, evaluated in the current row and only then, or `null` without one. A `null` found in the other row is returned as it is: the default stands for a missing row, not for a missing value.
- **Ties.** Peers come in an unspecified order, as rows equal on every key of the query's `orderBy` do. `rank`, `denseRank`, `percentRank` and `cumulativeDistribution` are the same whatever that order is; `rowNumber`, `ntile`, `previous`, `next` and every frame depend on it. End the keys with one that identifies a row, such as an `id`; the schema cannot check this, as for `pagination`.
- **Parameters.** A frame count, an `offset` and `buckets` given as parameters are read once for the query. A frame count of `0` leaves no rows on that side, and a distance of `0` only the rows with the same key; binding a frame count or a distance below 0, an `offset` below 1 or `buckets` below 1 is an [execution error](#execution-errors).
- Over five rows with the totals `10`, `20`, `20`, `30`, `40`, ordered by total: `rowNumber` is 1 to 5; `rank` is 1, 2, 2, 4, 5 and `denseRank` 1, 2, 2, 3, 4; `percentRank` is `0`, `0.25`, `0.25`, `0.75`, `1` and `cumulativeDistribution` `0.2`, `0.6`, `0.6`, `0.8`, `1`; `ntile` with 2 buckets is 1, 1, 1, 2, 2; `sum` of the total with `{ "preceding": 1 }` is `10`, `30`, `40`, `50`, `70`; `previous` of the total is `null`, `10`, `20`, `20`, `30`, and `next` with the default `0` is `20`, `20`, `30`, `40`, `0`.

### Parameters

- A query is run with a value for every parameter it uses. A value is written exactly like a literal of the declared type, in the same one spelling: a JSON number for `integer`, the literal formats for `decimal` (a string within its range), `date`, `time`, `datetime` (in UTC) and `uuid` (in lower case). A list parameter is a JSON array of non-`null` values of the element type, possibly empty, and may repeat a value.
- A nullable parameter may be bound to `null`; a non-null one may not. Bound values that the query does not use are ignored.
- One parameter name has one type in the whole document, subqueries included.

### Names and sources

- Each source of a query, the main query or a subquery, has a name: its `alias`, or its entity or subquery name when there is no alias. These names are unique within the query, and fields are referenced through them only: a source with an alias cannot be referenced by its entity or subquery name.
- Subquery names are unique in the document. A subquery may read entities and the subqueries declared before it; a recursive subquery also reads itself, in its `next`; the main query may read every subquery.
- A subquery's columns are its `select` (or `aggregate`) aliases, each with the type its expression declares.
- The columns of a combined query are those of its inputs, matched by alias, in the order of its first input. Each has the least type that accepts the column in every input. The columns of inline rows are those of its rows, matched and typed in the same way.
- Names compare exactly, code point by code point.

## Validation

The schema checks everything about a query's shape and types. The interpreter checks what depends on the catalog, on parameter values or on names:

| Rule | Checked by |
|---|---|
| Shape of every node, literal formats, unknown keys | schema |
| Operand and result types, nullability, implicit conversions | schema |
| Each operator declares exactly the type it yields from its operands | schema |
| Where fields, keys and aggregates may appear (contexts) | schema |
| Only the main query declares subqueries; a source is an entity or a subquery | schema |
| A combined query names one set operation over two or more queries and has no other clause | schema |
| A subquery is a query, inline rows or recursive; a cell of an inline row is a typed literal or a parameter | schema |
| A recursive subquery has `seed`, `next` and `maxDepth`; `next` has no `orderBy`, `distinctBy`, `pagination`, `aggregate` or window functions, and no aggregates or `having` without `groupBy`; a literal `maxDepth` is 1 or more | schema |
| `pagination` has an `orderBy`, and so do `first`, `last` and `concatAll`; a subquery has `orderBy` only with `pagination` or `distinctBy`; `distinctBy` lists each alias once | schema |
| One spelling: no `"nullable": false`, `and` / `or` with two conditions or more, no defaults written out (`over`, `direction`, `distinct`, `"skip": 0`, a `mode` of `round` naming its default rule, a zone that is UTC), one spelling of each literal value, at least one value and no repeated value in a list literal, at most one non-null `coalesce` operand; `integer` literals within 64 bits, `decimal` literals within 28 digits | schema |
| A literal `fraction` of a percentile is a `decimal` from 0 to 1 | schema |
| A window is written only in a plain query and names a partition, an order or a frame; an aggregate's window has an order exactly when it has a frame or a range; a ranking function, `previous` and `next` have a window with an order and no frame or range | schema |
| A frame has a side, not `"all"` on both, and a count of 1 or more; a literal `offset` is 2 or more and literal `buckets` 1 or more | schema |
| A window has a `frame` or a `range`, not both; a range has one sort key that declares `integer`, `decimal`, `date` or `datetime`, and distances written for that type, each above zero | schema |
| A literal regular expression uses only the constructs of [the dialect](#regular-expressions), and a literal `group` is 1 or more | schema |
| A `zone` is a `string` expression on an operator that reads a `datetime`; a literal one is a [time zone name](#time-zones) of the list in the schema | schema |
| A regular expression is well formed (its parentheses balance, its ranges and counted quantifiers are in order) and has the `group` that is asked for; for a parameter, when it is bound | interpreter |
| A `zone` parameter is bound to a time zone name of that list, or to `UTC` | interpreter |
| Entities, fields and parameters exist and have the declared types; a parameter used in several places has one type | interpreter |
| A parameter value is written like a literal of its type: one spelling, a `decimal` within its range, a `datetime` in UTC | interpreter |
| A `pagination` parameter is bound to `skip` ≥ 0 / `take` ≥ 1, a `fraction` parameter to a value from 0 to 1, a frame count or range distance parameter to 0 or more, and an `offset`, `buckets` or `maxDepth` parameter to 1 or more | interpreter |
| Each field reference declares exactly the nullability the field has at that point, outer joins included | interpreter |
| `groupBy` aliases are unique; a group key reference names one of them and repeats the type of its expression | interpreter |
| Subquery names are unique; a subquery reads only from earlier ones, and a recursive one also from itself, in `next` | interpreter |
| The `next` of a recursive subquery reads the subquery exactly once, in `from` or a join and not on the optional side of an outer join, and its `seed` does not read it; `next` has the aliases of `seed`, each once, with types the seed's columns accept | interpreter |
| Source names are unique within a query, and an aliased source is referenced by its alias | interpreter |
| A field references a source introduced at that point: a join's `on` sees `from`, the earlier joins and the joined source; later clauses see every source | interpreter |
| A subquery references only its own sources, never one of the query that reads it (a correlated reference is an error) | interpreter |
| Referenced subquery columns exist with the declared types | interpreter |
| The inputs of a set operation, and the rows of an inline subquery, have the same column aliases, each once, and the types of each column agree up to the implicit conversions | interpreter |
| Column aliases are unique within a `select` (and within an `aggregate`) | interpreter |
| Each `distinctBy` entry, and each `column` of an `orderBy`, is an alias of the query's `select` | interpreter |

The interpreter's part needs no type inference. Besides lookups, it tracks which sources are on the optional side of an outer join at each point of the query. Every expression declares its type, and the schema has already checked every declaration that does not depend on the catalog: each operator against its operands. A `select` column (referenced as a subquery column) and a `groupBy` key (referenced as `{ "key": <alias> }`) have the type of their expression. The interpreter only compares names and the declared types of fields, parameters and key references against the catalog, the `groupBy` list and the subquery headers, and reads the type of every other node as declared.

### Not specified yet

- how results are encoded for transport; literals and parameters write a `decimal` as a string, results may follow;
- the longest string a query may produce: `repeat`, `padStart`, `padEnd` and `concatAll` can ask for more than an interpreter holds;
- other string functions (matching with `%` and `_` wildcards);
- a time zone for a range frame over a `datetime` key with a distance in `months`, which counts months in UTC;
- the release of the IANA time zone database behind the rules of a zone: rules for future dates change when a government changes them, and rules for the past are sometimes corrected, so two interpreters with different releases may give different local times for the instants those changes touch. The names are fixed by the schema;
- whether a `zone` parameter or a computed zone may hold a name outside the list, such as an older link the interpreter's database still has;
- the version of the Unicode Character Database behind `upper`, `lower`, `foldCase`, `normalize` and `removeDiacritics`: a code point that a later version assigns, or gives a case mapping, a folding or a decomposition, may be converted differently by two interpreters. Text of code points that both versions assign is normalized the same way by both;
- other windows: one in a grouped query, a frame or a range that leaves out the current row, a range over a `time` key or with an open bound, the n-th value of a frame;
- other recursion: dropping rows that were already produced, detecting a cycle by a key, subqueries that read each other;
- Correlated subqueries are not part of the language: a reference from a subquery to a source of the query that reads it is an error.

## Tooling

| Path | Purpose |
|---|---|
| `tools/generate_schema.py` | Generates `PureQL-Specification.json`. Edit this file, never the schema |
| `tools/time_zones.txt` | The time zone names a literal `zone` may hold, read by the generator |
| `samples/valid/` | Queries that must be accepted: the [samples](#samples) (`.json`) and valid tests (`.jsonc`) |
| `samples/invalid/` | Queries that must be rejected, each a valid query with one thing broken (`.jsonc`) |
| `.github/workflows/validate.yml` | Runs on every pull request: checks formatting, then validates both directories |
| `.github/workflows/release.yml` | Runs on a version tag: validates again and publishes a release |
| `CHANGELOG.md` | The changes of each release |

```bash
python3 tools/generate_schema.py   # after changing the generator
npx --yes @prantlf/jsonlint@17.0.1 --check --indent 2 --trailing-newline --no-duplicate-keys PureQL-Specification.json
npx --yes @prantlf/jsonlint@17.0.1 --check --continue --indent 2 --trailing-newline --no-duplicate-keys "samples/valid/*.json"
npx --yes ajv-cli@5.0.0 test --spec=draft2020 --strict=false -s PureQL-Specification.json -d "samples/valid/*.json" -d "samples/valid/*.jsonc" --valid
npx --yes ajv-cli@5.0.0 test --spec=draft2020 --strict=false -s PureQL-Specification.json -d "samples/invalid/*.jsonc" --invalid
```

The generator needs Python; validation needs only Node.js. The schema has a root `version` keyword, which JSON Schema does not define, so a validator in strict mode must allow it (`--strict=false` for ajv). On every pull request CI also checks that `PureQL-Specification.json` is formatted exactly as the generator writes it, with 2-space indent, a final newline and no duplicate keys, and that every sample is formatted the same way, and fails with a diff otherwise. `jsonlint --in-place` with the same options formats a new sample. It runs the two ajv commands on every pull request and before every release: everything in `samples/valid/` must pass, everything in `samples/invalid/` must fail. `samples/valid/155_deep_nesting.jsonc` nests `equal(if(…))` 30 levels deep and guards against exponential validation time; `samples/valid/164_deep_operand_chains.jsonc` and `samples/invalid/0330_deep_malformed_operand_type.jsonc` do the same for other operators and for a malformed node. The other `deep_` tests guard the same way with chains 30 levels deep of numeric operators (`165`), `and` / `or` / `not` (`188`), `coalesce` (`189`), `round` (`190`) and `if` over aggregates (`191`); the invalid `*_deep_*` tests (`0329`, `1652`–`1655` and later ones) break only the innermost node of such a chain, so a validator must still reach it.

**Releases.** Each release is a GitHub release named after its version, with no `v` prefix, and has `PureQL-Specification.json`, `samples.zip` (the samples of `samples/valid/`), `README.md` and `CHANGELOG.md` as assets. A preview version is `major.minor.patch-preview.major.minor.patch`, e.g. `0.1.0-preview.3.0.0`, and is published as a pre-release. The schema's root `version` is its version and its `$id` its download URL, `https://github.com/kudima03/PureQL-Specification/releases/download/<version>/PureQL-Specification.json`, so a client can pin the exact schema it validates against. A query document is the bare query: it has no `$schema` key, which would be rejected like any unknown property, so the schema is given to the validator rather than named in the query. The changes of each version are in [`CHANGELOG.md`](CHANGELOG.md).

**Reading the schema.** Every definition is short and named after what it checks. `expr@row` is any expression in row context (likewise `@projection`, `@group` and `@total`); it sends an operator node to `operator@row`, which sends it to the section it belongs to (`operator.string@row`, `operator.arithmetic@row`, …) and from there to its own definition, and a leaf to `leaf@row`. An operator definition lists its signatures by declared type: in `add@row`, a node declaring `decimal?` is checked by `add.decimal.nullable@row`. A position that expects a type is `decimal.nullable@row`: an expression of row context whose declared type `accepts.decimal.nullable`. `declares.*` and `accepts.*` read only the `type` a node declares.

Each invalid test is a valid base query with exactly one thing broken, written as JSONC: a `//` comment describing what is broken, then the bare query. A new test takes the next free number. `samples/valid/184`–`187` use every operator in every signature, and every aggregate, once in each context (a `groupBy` key, a plain select, a grouped select, a total query). The invalid tests after `0411` break one thing at a time in each context: an unknown property, a missing operand, an operand of the wrong type or with a malformed value, a field, group key or aggregate where the context has none, a declared type that is not the exact one, `in` lists of every kind, and the clauses of each kind of query. They were chosen by deleting or loosening each constraint of the schema in turn and keeping the tests that notice it.
